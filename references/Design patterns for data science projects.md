# Design patterns hide inside scikit-learn's API

The well-known design patterns of data science are mostly classic Gang of Four (GoF) patterns wearing library-specific clothing: scikit-learn's estimator API is a **Template Method + Strategy** combination, its `Pipeline` is the field's signature composition pattern, Keras and PyTorch Lightning callbacks are the **Observer** pattern, pandas' `read_*` functions are **Adapters**, and PyTorch's `Dataset`/`DataLoader` pair is **Factory + Iterator** ([Eugene Yan](https://eugeneyan.com/writing/design-patterns/); [Király et al., arXiv:2101.04938](https://arxiv.org/pdf/2101.04938)). For a project like yours — Wine Quality, scikit-learn baseline, MLflow tracking in a Cookiecutter Data Science (ccds) layout — the practical upshot is that you rarely need to *implement* GoF patterns from scratch; you need to **conform to the estimator contract and compose with `Pipeline`**, which gives you Strategy-style model swapping, leak-free preprocessing, and grid-searchable hyperparameters for free. Around that core sit a small set of DS-specific idioms with strong canonical sourcing: separate configuration from code, keep raw data immutable and treat the analysis as a DAG, confine learning to `fit` and reuse via `transform`, control randomness explicitly, and graduate repeated notebook code into tested modules ([scikit-learn Common Pitfalls](https://scikit-learn.org/stable/common_pitfalls.html); [ccds Opinions](https://cookiecutter-data-science.drivendata.org/opinions/)). The anti-pattern canon is equally settled: notebook hidden state and copy-paste duplication ([KDnuggets](https://www.kdnuggets.com/2019/11/notebook-anti-pattern.html)), and the system-level debts — glue code, pipeline jungles, entanglement, configuration debt — named in Google's Hidden Technical Debt paper ([Sculley et al., NeurIPS 2015](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)). Architecture and MLOps patterns (Transform, Workflow Pipeline, experiment tracking, model registry) matter here mainly as the *reasons* the code patterns exist — they are what the code-level discipline buys you later.

## GoF patterns are the load-bearing structure of ML libraries

The most defensible mapping of classic patterns onto ML code comes from two sources that converge: Eugene Yan's taxonomy of design patterns in ML libraries, and the academic treatment of toolbox architecture by Király et al., which traces scikit-learn's design directly to Gamma et al.'s pattern catalog. Király et al. call the combination of a base-class template with interchangeable concrete estimators "the central pattern used in contemporary toolbox architectures" and "defining for scikit-learn-like toolboxes" — formally, **Template Method** (the base class and mixins fix the universal interface points) **plus Strategy** (any estimator of the same kind can be swapped in at runtime) ([Király et al.](https://arxiv.org/pdf/2101.04938)). You see the Template Method concretely in scikit-learn's mixins: `TransformerMixin` provides `fit_transform()` by calling `fit().transform()`, and `ClassifierMixin`/`RegressorMixin` provide default `score()` methods, so a concrete class only fills in `fit`, `predict`, or `transform` ([scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html)). The Strategy side is what lets you swap `LogisticRegression` for `RandomForestClassifier` in a Wine Quality experiment with a one-line change — the uniform API across 200+ estimators is the point, and sklearn enforces it by **duck typing rather than `isinstance()` checks**: an estimator need not inherit from any sklearn class to work in a `Pipeline`, as long as it honors the interface ([scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html); [Buitinck et al., arXiv:1309.0238](https://arxiv.org/abs/1309.0238)).

The second pillar is the **Pipeline pattern**: chaining transformers and a final estimator behind one `fit`/`predict` surface. Composition works because every step shares the same contract — `fit(X, y)` everywhere, `transform` on transformers, `predict` on the final estimator, and `get_params`/`set_params` so `GridSearchCV` can tune hyperparameters across all steps without special wiring ([scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html); [Eugene Yan](https://eugeneyan.com/writing/design-patterns/)). Related and worth knowing is sklearn's **Prototype-like cloning**: meta-estimators such as `GridSearchCV` use `clone()` to create unfitted copies that preserve only constructor arguments, preventing state leakage between cross-validation trials ([scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html)).

The remaining GoF mappings each have a named, citable home. **Observer** appears as training callbacks: Keras ships roughly 14 built-ins (`EarlyStopping`, `ModelCheckpoint`, `TensorBoard`, `ReduceLROnPlateau`...) that hook `on_epoch_begin/end` and friends, passed as a list to `model.fit(callbacks=...)` ([Keras Callbacks API](https://keras.io/api/callbacks/)), and PyTorch Lightning's hooks "insert custom behavior at specific points during the training process without modifying the core training loop" ([Lightning hooks docs](https://lightning.ai/docs/pytorch/latest/common/hooks.html)). **Adapter** is pandas' ~20 `read_*` functions and Spark's data-source readers, which normalize heterogeneous formats into one DataFrame interface ([Eugene Yan](https://eugeneyan.com/writing/design-patterns/)). **Factory** covers PyTorch's `Dataset` base class and Hugging Face's `Dataset`; a humbler, directly reusable idiom maps model-name strings to sklearn classes in a factory function so experiment configs can name the model to train ([Eugene Yan](https://eugeneyan.com/writing/design-patterns/); [KDnuggets](https://www.kdnuggets.com/breaking-out-of-beginner-python-patterns-for-intermediate-data-scientists)). **Iterator** is PyTorch's `DataLoader`, decoupling traversal (batching, shuffling) from the container; **Decorator** shows up as `@lru_cache`, `@pytest.fixture`, and custom timing decorators ([Eugene Yan](https://eugeneyan.com/writing/design-patterns/)). Two honest caveats: Facade (e.g., `model.fit` hiding a training loop) and Singleton (e.g., MLflow's module-level `mlflow.log_metric` acting on a single active run) are plausible readings but no authoritative source names them as such, and the "Machine Learning Design Patterns" book (Lakshmanan, Robinson & Munn, O'Reilly 2020) — 30 patterns across data representation, training, serving, reproducibility, and responsible AI — is mostly an *architecture* catalog; only Transform, Workflow Pipeline, Checkpoints, and Stateless Serving Function prescribe code-level structure ([O'Reilly](https://www.oreilly.com/library/view/machine-learning-design/9781098115777/); [companion repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)).

## Five idioms separate DS code from DS scripts

The first and most consequential idiom is **fit/transform separation to prevent data leakage**. scikit-learn's own pitfalls guide states the rule plainly: "never call fit on the test data" — scaling means, imputation values, and selected features must be learned from the training subset only, then applied to both subsets via `transform` ([scikit-learn Common Pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)). The guide's demonstration is memorable: `SelectKBest` fit on the full dataset before splitting produced **76% accuracy on completely random targets**, versus the correct ~50% when fit on the training fold only. The structural fix is the idiom's second half: put *all* preprocessing inside a `Pipeline` so cross-validation automatically fits each step on the right subset — "the scikit-learn pipeline is a great way to prevent data leakage as it ensures that the appropriate method is performed on the correct data subset" ([scikit-learn Common Pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)). For a Wine Quality baseline, this means your `StandardScaler` + model belongs in one `Pipeline` object that MLflow logs as a single artifact, not two separately-fitted pieces.

Second, **constructor discipline**, the sklearn house rule worth copying into your own classes: `__init__` only stores parameters, unchanged — no validation, no mutation, no data-derived defaults; all real work happens in `fit()`. Every constructor kwarg is stored as a same-named attribute, learned state gets a trailing underscore (`coef_`), and internal state a leading one ([scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html)). This is the DS version of "no work in constructors," and it is precisely what makes cloning, grid search, and pipelines composable — violate it and `GridSearchCV` silently breaks.

Third, **configuration lives outside code**. Hydra "separates code from configuration, making experiments reproducible and composable," supporting hierarchical configs and runtime overrides, and it integrates with MLflow ([KDnuggets](https://www.kdnuggets.com/2023/03/hydra-configs-deep-learning-experiments.html)); combining pydantic validation with Hydra composition is documented practice ([Towards Data Science](https://towardsdatascience.com/configuration-management-for-model-training-experiments-using-pydantic-and-hydra-d14a6ae84c13)). At student-project scale, a `params.yaml` or a typed config module read by `train.py` captures the same idiom; the test is whether changing a hyperparameter requires editing logic. Secrets follow the same rule in stricter form: a git-ignored `.env` loaded with python-dotenv ([ccds Opinions](https://cookiecutter-data-science.drivendata.org/opinions/)).

Fourth, **explicit randomness**. Declare the RNG (`rng = np.random.RandomState(0)`) so results are reproducible — sklearn's guide shows that doing so guarantees a fixed score across runs — and prefer integers for CV splitters but RandomState instances for estimators when comparing algorithms fairly ([scikit-learn Common Pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)). Logged alongside your MLflow params, the seed makes every run re-creatable.

Fifth, **functional style on DataFrames and stateless modules**. Tom Augspurger's method-chaining essay argues for `.assign` and `.pipe` chains that read top-to-bottom like the execution flow, against intermediate-variable naming churn, and explicitly against `inplace=True` (it returns `None`, breaks chaining, and gives no memory guarantee) — while conceding the known cost that long chains hide intermediate values during debugging ([Tom Augspurger](https://tomaugspurger.net/posts/method-chaining/)). At module scale, Made With ML's canonical refactor splits notebook code into `config.py`, `data.py`, `train.py`, `evaluate.py`, `predict.py` and peers, because "scripts are stateless, requiring explicit variable passing" and execute linearly rather than by cell order ([Made With ML](https://madewithml.com/courses/mlops/scripting/)) — essentially the file layout ccds already gives you.

## The anti-pattern canon: notebooks, leakage, and 95% glue

The notebook critique is the field's most-rehearsed anti-pattern. Kristina Young's "Notebook Anti-Pattern" names six failure modes: reliance on notebook-wide **mutable state that changes with every cell execution**, code duplication because notebooks cannot import each other, lack of testing, unreadable pull-request diffs, merge-conflict-prone collaboration, and manual dependency tracking — with the recommendation to keep notebooks for experimentation and "stick to software engineering principles and frameworks for bringing things to production" ([KDnuggets](https://www.kdnuggets.com/2019/11/notebook-anti-pattern.html)). Academic work corroborates this: notebook bad practices arise at three levels (general Python conventions, notebook structure, and ML-specific reproducibility), and notebooks "lack rigorous enforcement of coding standards due to limited integration with linters or code-smell detectors" ([arXiv:2509.11748](https://arxiv.org/html/2509.11748v1)). Crucially, the cure is not banning notebooks — ccds's own position is that notebooks are for exploration while "source code is superior for replicability because it is more portable, can be tested more easily, and is easier to code review," so you refactor the good parts into the package and import them back ([ccds Opinions](https://cookiecutter-data-science.drivendata.org/opinions/)).

At the system level, the vocabulary comes from Sculley et al.'s Hidden Technical Debt paper, the single most cited anti-pattern source in ML. Its headline figure: "a mature system might end up being (at most) **5% machine learning code and (at least) 95% glue code**" ([Sculley et al., NeurIPS 2015](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)). Its named debts include **entanglement/CACE** ("Changing Anything Changes Everything" — no feature is independent, so isolated improvements are impossible), **pipeline jungles** (data prep degrading into a tangle of scrapes, joins, and intermediate outputs, remediable only by holistic redesign), **dead experimental codepaths** (accumulated conditional branches exploding complexity), **configuration debt** (config often exceeding model code in line count), correction cascades, undeclared consumers, and hidden feedback loops ([Sculley et al.](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)). Even in a single-student project, the small-scale versions are recognizable: copy-pasted preprocessing cells are a nascent pipeline jungle, commented-out model variants are dead experimental codepaths, and hyperparameters scattered across cells are configuration debt. The remaining canon members are code-level: **pre-split preprocessing leakage** (the 76%-on-random-labels failure above), **uncontrolled randomness**, **hardcoded paths and committed secrets** (ccds's `.env` rule exists precisely against these), and **`inplace=True` mutation** ([scikit-learn Common Pitfalls](https://scikit-learn.org/stable/common_pitfalls.html); [ccds Opinions](https://cookiecutter-data-science.drivendata.org/opinions/); [Augspurger](https://tomaugspurger.net/posts/method-chaining/)).

## ccds is the DAG opinion written as folders; MLflow is the lineage pattern written as code

Since you are keeping the ccds structure as-is, the settled context in one paragraph: ccds encodes its two core opinions directly in the filesystem. "Raw data must be treated as immutable" and the analysis should be "a directed acyclic graph (DAG)" — so data flows one way through `data/raw` ("original, immutable data dump") → `interim` → `processed`, data stays gitignored, and anyone can reproduce the outputs from code plus raw data alone ([ccds Opinions](https://cookiecutter-data-science.drivendata.org/opinions/); [ccds homepage](https://cookiecutter-data-science.drivendata.org/)). The v2 template's source package (`config.py`, `dataset.py`, `features.py`, `modeling/train.py`, `modeling/predict.py`, `plots.py`) is where the code patterns above land: the Factory idiom and config separation live in `config.py`, pure DataFrame transformations in `features.py`, the Pipeline-wrapped estimator and MLflow logging in `modeling/train.py`, and notebooks (named `<step>-<ghuser>-<description>.ipynb` so lexicographic order encodes execution order) import from the package rather than duplicating it ([ccds homepage](https://cookiecutter-data-science.drivendata.org/); [ccds Opinions](https://cookiecutter-data-science.drivendata.org/opinions/)). Notably, the `train.py`/`predict.py` split *is* the fit/transform separation at file granularity.

The architecture and MLOps patterns earn mention here exactly where they manifest in code. The ML Design Patterns book's **Transform** pattern "enforces the separation of inputs, features, and transforms and making the transformations persistent in order to simplify moving an ML model to production" ([O'Reilly](https://www.oreilly.com/library/view/machine-learning-design/9781098115777/)) — in sklearn terms, that is simply persisting the fitted `Pipeline` so serving reuses training's exact transformation code, which is also Google's Rules of ML skew-prevention prescription (Rule #32: reuse code between training and serving; Rule #29: log serving features) ([Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)). **Workflow Pipeline** (every step as a DAG node) appears in your project as the Makefile/script chain from `dataset.py` to `train.py` ([ml-design-patterns repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)). On the MLflow side, two workflow patterns have direct code shape: **experiment tracking** — runs grouped into experiments with logged params, metrics, and artifacts, which CD4ML prescribes as the way to manage parallel experiments ([martinfowler.com: CD4ML](https://martinfowler.com/articles/cd4ml.html)) — and the **model registry promotion pattern**, where a registered model accumulates versions and a mutable alias like `@champion` designates the serving version, with promotion being an alias reassignment and full lineage back to "which MLflow experiment and run produced the model" ([MLflow Model Registry docs](https://mlflow.org/docs/latest/ml/model-registry/)). In maturity-model terms, a tracked, script-driven, reproducible training setup is exactly the gate Microsoft calls Level 2 ("experiment results are tracked," training code and models version controlled), one level above notebook-manual Level 0 ([Microsoft MLOps maturity model](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/mlops-maturity-model); [Google Cloud MLOps](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)). Finally, two patterns from the book are cheap to adopt in code now: **Heuristic Benchmark** (log a trivial baseline — mean predictor or majority class — as an MLflow run so every model has an explainable comparison) and **Repeatable Sampling** (deterministic, hash- or seed-based splits logged as params) ([ml-design-patterns repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)). A worked example applying GoF patterns specifically to MLflow experiment tracking exists on GitHub if you want a reference implementation ([DesignPatterns-MLFlow-for-ExperimentTracking](https://github.com/UribeAlejandro/DesignPatterns-MLFlow-for-ExperimentTracking)).

## Conclusion

The unifying insight is that data science's "design patterns" operate at one remove from the GoF catalog: the patterns are already implemented inside scikit-learn, Keras, pandas, and MLflow, and the practitioner's job is *conformance and composition* — honor the estimator contract, compose inside `Pipeline`, externalize config, and let the library's Template Method, Strategy, and Observer machinery do the structural work. That reframing explains why the field's loudest literature is about anti-patterns rather than patterns: the failure mode is not choosing the wrong pattern but bypassing the existing ones (fitting outside the pipeline, mutating state in notebooks, hardcoding config), which is exactly how Sculley's glue code and configuration debt accumulate.

For the Wine Quality project specifically, the patterns compose into a short checklist that costs little and is defensible line-by-line from canonical sources: one `Pipeline` holding preprocessing plus model, a config file or module as the single source of hyperparameters, a logged random seed, a factory function mapping config strings to estimators, a heuristic-baseline MLflow run, and notebooks that import from the package instead of redefining it. Everything heavier — feature stores, continuous training, shadow deployments — is the same discipline at organizational scale, and adopting the code-level versions now is precisely what the maturity models describe as the path from Level 0 to Level 2.
