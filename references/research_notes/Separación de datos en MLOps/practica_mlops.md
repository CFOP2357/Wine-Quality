# Data Splitting (Train/Validation/Test) in Production MLOps Practice

Research notes on where/how the test set is actually used in production ML pipelines, and what splitting practices MLOps authorities recommend. All claims carry an inline source URL; inferences and source caveats are flagged explicitly.

**Source caveat:** For Chip Huyen's *Designing Machine Learning Systems* (O'Reilly, 2022), quotes come from a detailed public chapter-by-chapter summary on GitHub (serodriguez68/designing-ml-systems-summary) plus Huyen's own blog, not from the book's paywalled text itself. The summary tracks the book's chapter structure (Ch. 5 feature engineering/leakage, Ch. 6 offline evaluation, Ch. 9 continual learning & test in production) and is treated here as a faithful secondary source.

## 1. Model validation in Google's MLOps maturity model and TFX

### Takeaway
In Google's canonical MLOps architecture, "model validation" is an explicit, automatable pipeline gate (required from maturity Level 1 onward) that evaluates the newly trained candidate on a holdout test set and compares its metrics against the current production/baseline model before promotion; TFX implements exactly this with the Evaluator component, which "blesses" a model only if it beats the baseline on the eval split, and the Pusher deploys only blessed models. Neither Google's article nor the TFX docs specify how the eval dataset is refreshed over time — in TFX it is simply the eval split that ExampleGen produces from each new ingested dataset.

### Cited Findings
- Google's model validation step consists of "Producing evaluation metric values using the trained model on a test dataset to assess the model's predictive quality" and "Comparing the evaluation metric values produced by your newly trained model to the current model, for example, production model, baseline model, or other business-requirement models" — [Google Cloud Architecture Center, MLOps: Continuous delivery and automation pipelines in ML](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- The same article's model evaluation step: "The model is evaluated on a holdout test set to evaluate the model quality," producing "a set of metrics to assess the quality of the model" — [Google Cloud Architecture Center](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- The validation gate's purpose is to "make sure that the new model produces better performance than the current model before promoting it to production," plus checking that "the performance of the model is consistent on various segments of the data" and testing deployment/infrastructure compatibility — [Google Cloud Architecture Center](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Maturity levels: Level 0 (manual) has no automated validation; Level 1 (ML pipeline automation) introduces automated data validation and model validation as required steps; Level 2 adds CI/CD around the pipeline. Automated model validation appears beginning at Level 1 — [Google Cloud Architecture Center](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- The article also mandates an online stage: "In addition to offline model validation, a newly deployed model undergoes online model validation—in a canary deployment or an A/B testing setup—before it serves prediction for the online traffic." — [Google Cloud Architecture Center](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- TFX Evaluator: "When validation is enabled, the Evaluator compares new models against a baseline (such as the currently serving model) to determine if they're 'good enough' relative to the baseline. It does so by evaluating both models on an eval dataset and computing their performance on metrics (e.g. AUC, loss)." — [TFX Evaluator guide](https://www.tensorflow.org/tfx/guide/evaluator)
- "If the new model's metrics meet developer-specified criteria relative to the baseline model (e.g. AUC is not lower), the model is 'blessed' (marked as good), indicating to the Pusher that it is ok to push the model to production." — [TFX Evaluator guide](https://www.tensorflow.org/tfx/guide/evaluator)
- Evaluator inputs: "An eval split from Examples," "A trained model from Trainer," and "A previously blessed model (if validation to be performed)"; thresholds are configured per metric (value thresholds and change-vs-baseline thresholds, e.g. `GenericChangeThreshold(direction=HIGHER_IS_BETTER, absolute=-1e-10)`), and "validation will be performed against all of the metrics and slices that were defined." — [TFX Evaluator guide](https://www.tensorflow.org/tfx/guide/evaluator)

### Inferences
- Because the TFX Evaluator consumes "an eval split from Examples" produced by ExampleGen on each pipeline run, in a continuous-training pipeline the eval set is implicitly refreshed every time new data is ingested: candidate and baseline are both scored on the *current* eval split, not on a frozen historical test set. (Inference from the Evaluator input spec; the docs do not state a refresh policy explicitly.)
- The champion/challenger comparison ("not worse than the currently serving model") means the test set's production role is primarily *relative gating*, not absolute reporting: it decides promotion, run after run.

### Gaps
- Neither the Architecture Center article nor the TFX docs prescribe how to compose or refresh the test dataset across retraining cycles (e.g., fixed vs rolling window); the Architecture Center article "mentions new data triggers retraining but doesn't detail test set composition strategies."

## 2. Chip Huyen on splitting: temporal vs random, leakage, split-before-preprocess

### Takeaway
Huyen treats bad splitting as a *data leakage* problem: for time-correlated data, split by time, not randomly, because random splits let future information leak into training; and perform preprocessing (scaling, imputation, oversampling) only *after* splitting, using statistics from the training split alone.

### Cited Findings
- Definition: "Data leakage is when a model gains an unfair performance advantage during training, validation and testing by learning to exploit information that 'leaks' the real label of the data." — [DMLS summary, Ch. 5](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/05-feature-engineering.md)
- Core rule: "Generally speaking, if a label's value is correlated with time, you probably want to split your data into train, validation and test datasets by time and not randomly." — [DMLS summary, Ch. 5](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/05-feature-engineering.md)
- Illustration (stock prediction): if predicting a stock's price from other stocks' behavior over the previous 6 days, a random split can include other companies' day-7 prices in training — "giving the model unfair future knowledge unavailable at inference time." — [DMLS summary, Ch. 5](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/05-feature-engineering.md)
- Scaling before splitting leaks: computing scalers on the entire dataset before splitting "encodes information about maximum, minimum, and average values that should remain unknown to the model during validation and testing." — [DMLS summary, Ch. 5](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/05-feature-engineering.md)
- Imputation leaks: using statistics from validation/test splits to fill missing training data leaks information that shouldn't influence training. — [DMLS summary, Ch. 5](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/05-feature-engineering.md)
- Duplication and groups: "Duplication is very common in industry and research datasets"; always check for duplicates before and after splitting, perform oversampling only after splitting; related samples (e.g., multiple CT scans of one patient) split across train/test create group leakage even without exact duplicates. — [DMLS summary, Ch. 5](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/05-feature-engineering.md)
- Detection: investigate features with unusually high label correlation via ablation studies; watch for suspicious performance jumps when adding features. — [DMLS summary, Ch. 5](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/05-feature-engineering.md)
- Test-set discipline: "NEVER use your test split to tune hyperparameters. Choose the parameters based on your validation set and only use the test set to assess the final performance." — [DMLS summary, Ch. 6](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/06-model-development-and-offline-evaluation.md)

### Inferences
- Huyen's framing implies the correct pipeline ordering is: split first (by time if time-correlated, by group if grouped) → fit preprocessing on train only → apply to val/test. This matches the leakage causes she enumerates, though the summary phrases it as a list of anti-patterns rather than a single ordered recipe.

### Gaps
- The exact verbatim wording from the book itself (pages/chapter text) could not be quoted directly; the O'Reilly text is paywalled, so quotes are from the GitHub summary.

## 3. Google's Rules of ML on evaluation data

### Takeaway
Rules of ML explicitly prescribe temporal evaluation: test on data collected *after* the training period (Rule #33), and use the train→holdout→next-day→live performance deltas as diagnostic instruments (Rule #37); final launch decisions rest on A/B-tested product metrics, not offline metrics alone (Rule #39).

### Cited Findings
- Rule #33: "If you produce a model based on the data until January 5th, test the model on the data from January 6th and after." Performance measured this way better reflects what the system will do in production. — [Rules of ML, developers.google.com](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Rule #37 ("Measure Training/Serving Skew") decomposes skew into three deltas: (a) training vs holdout performance, (b) holdout vs "next-day" data (should guide regularization tuning), (c) "next-day" vs live data (should be ~zero; a discrepancy indicates an engineering error). — [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Rule #29: "The best way to make sure that you train like you serve is to save the set of features used at serving time, and then pipe those features to a log to use them at training time." — [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Rule #34: for filtering tasks (e.g., spam), sacrifice short-term performance by labeling "1% of all traffic as held out" during serving to gather clean, unbiased training/eval data. — [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Rule #39: launch decisions depend on multiple metrics beyond the ML objective and require aligning algorithmic objectives with long-term product goals measured through A/B testing. — [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)

### Inferences
- Rules #33 + #37 together are Google's version of "the real test set is the future": the next-day (temporally out-of-sample) evaluation is treated as a standing pipeline measurement, not a one-time academic split. This also implies the eval data is refreshed daily by construction.

### Gaps
- None significant; the fetched rule texts for #33/#37 are partly paraphrased by the extraction except the verbatim Jan-5/Jan-6 sentence.

## 4. Repeatable/deterministic splitting (ML Design Patterns, "Repeatable Splitting")

### Takeaway
The Repeatable Splitting/Sampling pattern (Lakshmanan et al.) prescribes deterministic, hash-based splits — hash a well-chosen column (e.g., `FARM_FINGERPRINT`/`HASH` modulo 10 → 80/10/10) — because `RAND()`-style sampling, even seeded, is not reproducible on distributed, re-ordered, or growing data, and the choice of hash column doubles as leakage control (splitting by date or by entity keeps correlated rows together).

### Cited Findings
- "Repeatable Sampling" is Pattern #22 in the Reproducibility chapter (06_reproducibility) of *Machine Learning Design Patterns* (Lakshmanan, Robinson, Munn; O'Reilly 2020); "Continuous Model Evaluation" is Pattern #18 in the Resilience chapter (05_resilience) — [GoogleCloudPlatform/ml-design-patterns repo](https://github.com/GoogleCloudPlatform/ml-design-patterns); [O'Reilly book page](https://www.oreilly.com/library/view/machine-learning-design/9781098115777/); [research.google listing](https://research.google/pubs/machine-learning-design-patterns/)
- Why RAND() fails (Lakshmanan's original BigQuery article, the basis of the pattern): "The RAND() function returns different things each time it is run, so if you run the query again, you will get a different 80% of rows"; moreover "The order of rows in a BigQuery result set is not guaranteed—it is essentially the order in which different workers return their results," so even with random seeds "you'll still not get repeatable results." — [O'Reilly: Repeatable sampling of data sets in BigQuery for ML](https://www.oreilly.com/content/repeatable-sampling-of-data-sets-in-bigquery-for-machine-learning/)
- The prescription: "use the last few digits of the HASH function on the field that you are using to split your data," e.g. `ABS(HASH(date)) % 10 < 8` for a repeatable 80% train split, "because the HASH function returns the same value any time it is invoked on a specific date." — [O'Reilly article](https://www.oreilly.com/content/repeatable-sampling-of-data-sets-in-bigquery-for-machine-learning/)
- Modulo bucketing for three sets: train `% 10 < 8` (80%), validation `% 10 == 8` (10%), test `% 10 == 9` (10%). — [O'Reilly article](https://www.oreilly.com/content/repeatable-sampling-of-data-sets-in-bigquery-for-machine-learning/)
- Column choice is a modeling decision: hashing on `date` keeps whole days in one split; hashing on `arrival_airport` splits by airport — chosen to match what must not straddle the train/test boundary. — [O'Reilly article](https://www.oreilly.com/content/repeatable-sampling-of-data-sets-in-bigquery-for-machine-learning/)
- `FARM_FINGERPRINT` (the BigQuery function the book's pattern uses) "computes the fingerprint... using the Fingerprint64 function from the open-source FarmHash library, and the output of this function for a particular input will never change." — [GoogleSQL hash functions docs](https://docs.cloud.google.cn/spanner/docs/reference/standard-sql/hash_functions)

### Inferences
- Repeatable splitting is what makes the production model-validation gate meaningful: champion and challenger must be scored on the *same* examples, and a hash-based split guarantees that even when the underlying table grows between pipeline runs, a given row always lands in the same split. (Inference connecting the pattern to the gating practice in section 1.)
- Hash-on-well-chosen-column also prevents the group/temporal leakage Huyen describes: hashing on a grouping key (patient, day, user) is the mechanical implementation of "keep correlated rows in one split."

### Gaps
- The book chapter's own verbatim text for Pattern #22 (and its discussion of why `setting a random seed` alone is insufficient) could not be fetched (O'Reilly paywall; the companion Medium/TDS post returned 404). The 2016 O'Reilly article by the same author covers the same technique and is used as the primary citable source.

## 5. Test-set refresh and staleness across retraining cycles

### Takeaway
Authorities converge on three mitigations for eval-set staleness/overfitting: (a) refresh the validation and test sets periodically with fresh data (Google ML Crash Course), (b) make evaluation temporal by construction so eval data rolls forward automatically (Rules of ML #33/#34; Huyen's backtesting), and (c) accept that for continually retrained models a stationary test set "no longer suffices" and lean on production evaluation. Empirically, the feared adaptive overfitting to reused holdouts appears smaller than theory suggests (NeurIPS 2019 Kaggle meta-analysis), but the guidance to refresh persists.

### Cited Findings
- "The more you use the same data to make decisions about hyperparameter settings or other model improvements, the less confidence that the model will make good predictions on new data"; the guidance recommends collecting fresh data periodically to "refresh" both the validation and test sets. — [Google ML Crash Course, Dividing datasets](https://developers.google.com/machine-learning/crash-course/overfitting/dividing-datasets)
- Test set quality bar: "Large enough to yield statistically significant testing results," representative of real-world serving data, and "Zero examples duplicated in the training set." — [Google ML Crash Course](https://developers.google.com/machine-learning/crash-course/overfitting/dividing-datasets)
- Huyen: "Because you're updating your models to adapt to changing environments, a stationary test set no longer suffices" (Stage 4, continual learning); she recommends incorporating "backtest, progressive evaluation, test in production including shadow deployment, A/B test, canary analysis, and bandits." — [huyenchip.com, Real-time ML challenges and solutions](https://huyenchip.com/2022/01/02/real-time-machine-learning-challenges-and-solutions.html)
- Backtesting = using "the freshest labelled data that hasn't been seen by the model during training to test performance," but the belief that "backtesting is sufficient [to] avoid testing in production" is explicitly called out as a false assumption: "good performance on a static old test split does not guarantee good performance under the current data distribution conditions in production." — [DMLS summary, Ch. 9](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/09-continual-learning-and-test-in-production.md)
- ml-ops.org (ML Test Score-derived): monitor "slow degradation in model quality over many versions on a validation set" with a threshold, and test "for sudden performance drops in a new version of the ML model"; also "use an additional test set, which is disjoint from the training and validation sets. Use this test set only for a final evaluation," and ideally "separate the teams and procedures collecting the training and test data" to avoid methodology bleeding from train to test. — [ml-ops.org, MLOps Principles](https://ml-ops.org/content/mlops-principles)
- Empirical counterweight: a NeurIPS 2019 meta-analysis of test-set reuse across 100+ Kaggle competitions "showed little evidence of substantial overfitting" despite competitors repeatedly evaluating against the holdout. — [A Meta-Analysis of Overfitting in Machine Learning, NeurIPS 2019](https://papers.nips.cc/paper/9117-a-meta-analysis-of-overfitting-in-machine-learning)
- Rule #34 institutionalizes a *standing* fresh holdout: keep "1% of all traffic as held out" at serving time to produce clean evaluation/training data continuously. — [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)

### Inferences
- In production pipelines the dominant refresh mechanism is temporal, not curatorial: because retraining runs re-split newly ingested data (TFX eval split per run; Rule #33 next-day eval; backtests on freshest labels), the eval set is a rolling window as a side effect of continuous training, rather than a manually "refreshed" fixed file. (Inference from sections 1, 3 and the Huyen citations above; no source states this synthesis in one place.)
- The Kaggle meta-analysis suggests the bigger practical risk is not adaptive overfitting to a reused test set but *distribution staleness* — the test set no longer resembling serving data — which is exactly what temporal refresh addresses.

### Gaps
- I found no authoritative source giving a concrete refresh cadence (e.g., "rotate the test set every N retrains/months"); guidance is qualitative ("periodically," "freshest labelled data").

## 6. Online evaluation as the "real test": shadow, canary, A/B, continued evaluation

### Takeaway
All surveyed authorities treat offline test-set evaluation as necessary but insufficient: Google requires online model validation (canary/A-B) after offline validation, CD4ML describes shadow models and canary/blue-green releases, and Huyen catalogs shadow → canary → A/B → interleaving → bandits as the graduated "test in production" ladder. The *Continued/Continuous Model Evaluation* pattern closes the loop by scoring the deployed model on sampled live traffic with later-arriving ground truth.

### Cited Findings
- Google: "In addition to offline model validation, a newly deployed model undergoes online model validation—in a canary deployment or an A/B testing setup—before it serves prediction for the online traffic." — [Google Cloud Architecture Center](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- CD4ML (Sato, Wider, Windheuser on martinfowler.com): "You can deploy the new model side-by-side with the current one, as a shadow model, and send the same production traffic to gather data on how the shadow model performs before promoting it"; "Software release patterns such as Blue Green Deployment or Canary Releases can also be applied"; offline, "we can use these metrics to introduce Threshold Tests or ratcheting in our pipeline, to ensure that new models don't degrade against a known performance baseline" (their demo used "a simple PyUnit threshold test that breaks if the error rate goes above 80%... executed prior to publishing a new model version"); they also suggest teams "distribute a holdout dataset along with the model artifact, and allow the consuming application team to reassess the model's performance against the holdout dataset after it is integrated." — [martinfowler.com, CD4ML](https://martinfowler.com/articles/cd4ml.html)
- Huyen (Ch. 9): "To sufficiently test your models before making them widely available you need both pre-deployment offline evaluations AND testing in production. Offline evaluations alone are not sufficient," because "Production performance is much more than label-related performance. You still need to observe things like latency, user behaviour with the model and system integration correctness." — [DMLS summary, Ch. 9](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/09-continual-learning-and-test-in-production.md)
- Shadow deployment: "Deploy the challenger model in parallel with the existing champion model. Send every incoming request to both models but only serve the inference of the champion model... This is the safest way to deploy your models" (but doubles compute and can't measure user-interaction effects). — [DMLS summary, Ch. 9](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/09-continual-learning-and-test-in-production.md)
- A/B testing: challenger predictions "are shown to the users"; "The traffic split must be a truly randomized experiment"; cheaper than shadowing but "less safe than shadow deployments." Canary: "Slowly move traffic from the champion to the challenger (aka the canary). Monitor the performance metrics"; simplest to implement but "opens the possibility to not be rigorous in determining performance differences." Interleaving: Netflix found it identifies the best model "with considerably smaller sample size compared to traditional A/B testing." Bandits: dynamically exploit/explore per request; need "less data than A/B testing" (example given: 12K vs 630K samples) but are "much harder to implement." — [DMLS summary, Ch. 9](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/09-continual-learning-and-test-in-production.md)
- ml-ops.org: "ML models are canaried before serving," and teams should verify "an ML model successfully loads into production serving and the prediction on real-life data is generated as expected"; offline-online linkage requirement: "ML algorithm loss metrics (MSE, log-loss, etc.) should correlate with business impact metrics (revenue, user engagement, etc.)"; also "Testing that the model in the training environment gives the same score as the model in the serving environment." — [ml-ops.org, MLOps Principles](https://ml-ops.org/content/mlops-principles)
- "Continuous Model Evaluation" is Pattern #18 (Resilience chapter) in *Machine Learning Design Patterns* — [GoogleCloudPlatform/ml-design-patterns](https://github.com/GoogleCloudPlatform/ml-design-patterns); the book itself is at [O'Reilly](https://www.oreilly.com/library/view/machine-learning-design/9781098115777/)

### Inferences
- The offline test set and online evaluation form a two-stage filter with different nulls: offline validation answers "is the candidate at least as good as the champion on held-out data?" (cheap, safe, gates promotion), while online evaluation answers "does it actually move business/user metrics under real traffic?" (expensive, risky, gates full rollout). Rules of ML #39 and the ml-ops.org correlation requirement make explicit that the offline metric is only a proxy whose validity must itself be checked against online outcomes.
- Shadow deployment is effectively "test-set evaluation on tomorrow's data": same inputs as production, labels arrive later — i.e., the online analogue of Rule #33.

### Gaps
- The full prescriptive text of the Continued Model Evaluation pattern (sampling rate, ground-truth joining, retrain triggers) could not be retrieved: the book is paywalled, and the legacy Google Cloud AI Platform "continuous evaluation" docs page returned truncated/redirected content. The pattern's existence, placement, and intent are confirmed; its detailed mechanics are not quoted here.

## 7. Test set in experiment tracking: log every run, or hide until the end?

### Takeaway
The explicit written guidance (Huyen; Google's ML Crash Course; classic textbook practice) says to tune only on the validation set and touch the test set once for final assessment — Huyen's tracking checklist pointedly says to log metrics on "all non-test splits." I found no authoritative source endorsing the common tooling-driven habit of logging test metrics on every tracked run; conversely, production champion/challenger gates (TFX, Google MLOps) *do* re-score the eval/test split on every pipeline run, so the "touch once" ideal applies to interactive experimentation, while automated pipelines re-use (refreshed) eval splits continuously.

### Cited Findings
- Huyen's per-run tracking list: "Loss curve of train and each of the eval splits" and "Model performance metrics you care about on all non-test splits: accuracy, F1, perplexity," plus sample/prediction logs, speed, system metrics, and hyperparameter values over time. — [DMLS summary, Ch. 6](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/06-model-development-and-offline-evaluation.md)
- Huyen: "NEVER use your test split to tune hyperparameters. Choose the parameters based on your validation set and only use the test set to assess the final performance." — [DMLS summary, Ch. 6](https://github.com/serodriguez68/designing-ml-systems-summary/blob/main/06-model-development-and-offline-evaluation.md)
- Google ML Crash Course workflow: "Train model on the training set. Evaluate model on the validation set. Tweak model according to results on the validation set. Iterate... picking the model that does best on the validation set. Confirm the results on the test set." — [ML Crash Course, Dividing datasets](https://developers.google.com/machine-learning/crash-course/overfitting/dividing-datasets)
- ml-ops.org: "Use an additional test set, which is disjoint from the training and validation sets. Use this test set only for a final evaluation." — [ml-ops.org, MLOps Principles](https://ml-ops.org/content/mlops-principles)
- CD4ML documents experiment tracking with MLflow ("an API and a web interface to visualize the multiple experiment runs, along with their parameters and performance metrics") but does not prescribe which split's metrics to log per run. — [martinfowler.com, CD4ML](https://martinfowler.com/articles/cd4ml.html)
- Pedagogical consensus (secondary sources): the test set is "a very precious resource that should ideally never be touched until one time at the very end"; the validation set is "essentially used as a fake test set to tune the hyperparameters." — [Towards Data Science: Train, validation and test sets](https://medium.com/data-science/train-validation-and-test-sets-72cb40cba9e7); [Educative: why both validation and test sets](https://www.educative.io/answers/why-use-both-validation-and-test-sets-in-machine-learning)
- Counterweight for the strictness of the rule: the NeurIPS 2019 Kaggle meta-analysis found "little evidence of substantial overfitting" from repeated holdout evaluation in practice. — [NeurIPS 2019](https://papers.nips.cc/paper/9117-a-meta-analysis-of-overfitting-in-machine-learning)

### Inferences
- There is an unreconciled tension in practice: experiment-tracking UIs (MLflow run tables) make it trivial to log `test_*` metrics on every run, but the authorities quoted above implicitly or explicitly reserve test metrics for final/promotion-time evaluation. A defensible production synthesis, consistent with sections 1 and 5: log train+validation metrics per experiment run; compute test/eval-split metrics only in the automated validation gate (champion-vs-challenger), and mitigate the resulting test-set reuse by refreshing the eval split temporally each retraining cycle. This synthesis is my inference — no single source states it.

### Gaps
- No explicit MLflow (or other tracking-tool vendor) documentation was found that takes a position on whether test metrics should be logged for every run; vendor docs demonstrate metric logging generically. This specific question appears essentially unaddressed in authoritative MLOps literature.
