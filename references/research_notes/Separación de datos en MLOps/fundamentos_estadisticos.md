# Fundamentos estadísticos de la separación train/validation/test para selección y evaluación de modelos

Notas de investigación (fuentes canónicas: ESL, Goodfellow et al., Ng, scikit-learn, Raschka, JMLR/BMC). Las citas textuales se conservan en inglés original.

## ¿Qué prescriben las referencias canónicas (ESL, Goodfellow et al., Ng, scikit-learn)?

### Takeaway
Las cuatro fuentes canónicas coinciden en la misma arquitectura: el conjunto de entrenamiento ajusta parámetros, el de validación (dev) sirve para *seleccionar* (hiperparámetros, features, arquitecturas) y el de test sirve *exclusivamente* para la evaluación final del modelo elegido; cualquier decisión tomada con el test contamina su estimación de generalización.

### Cited Findings
- **ESL (Hastie, Tibshirani, Friedman), cap. 7**, distingue dos metas separadas: *model selection* (estimar el desempeño de distintos modelos para elegir el mejor) vs. *model assessment* (habiendo elegido el modelo final, estimar su error de generalización en datos nuevos); el libro completo está disponible gratis en el sitio de los autores — [ESL, hastie.su.domains](https://hastie.su.domains/ElemStatLearn/)
- ESL señala que es difícil dar una regla general para el tamaño de cada partición, pero que una división típica es 50% entrenamiento, 25% validación, 25% test — [SAS documentation citando a Hastie, Tibshirani y Friedman](https://documentation.sas.com/api/docsets/casactstat/v_040/content/casactstat_introcom_sect069.htm)
- ESL advierte: "Ideally, the test set should be kept in a 'vault,' and be brought out only at the end of the data analysis"; si el test se usa repetidamente para elegir el modelo con menor error de test, el error de test del modelo final "will underestimate the true test error, sometimes substantially" — citado y discutido en [Hardt & Recht, *Patterns, Predictions, and Actions* (arXiv:2102.05242)](https://arxiv.org/pdf/2102.05242); también recogido en [AI Wiki, test dataset](https://aiwiki.ai/wiki/test_dataset)
- **scikit-learn (User Guide, Cross-validation)**: "When evaluating different settings ('hyperparameters') for estimators… there is still a risk of overfitting *on the test set* because the parameters can be tweaked until the estimator performs optimally. This way, knowledge about the test set can 'leak' into the model and evaluation metrics no longer report on generalization performance." — [scikit-learn cross_validation docs](https://scikit-learn.org/stable/modules/cross_validation.html)
- scikit-learn, solución prescrita: "To solve this problem, yet another part of the dataset can be held out as a so-called 'validation set': training proceeds on the training set, after which evaluation is done on the validation set, and when the experiment seems to be successful, final evaluation can be done on the test set." — [scikit-learn cross_validation docs](https://scikit-learn.org/stable/modules/cross_validation.html)
- scikit-learn también advierte la desventaja del split de tres vías: "by partitioning the available data into three sets, we drastically reduce the number of samples which can be used for learning the model, and the results can depend on a particular random choice for the pair of (train, validation) sets" — motivación para cross-validation — [scikit-learn cross_validation docs](https://scikit-learn.org/stable/modules/cross_validation.html)
- **Goodfellow, Bengio y Courville, *Deep Learning*, §5.3 "Hyperparameters and Validation Sets"**: los ejemplos de test no deben usarse para tomar decisiones sobre el modelo, incluidos sus hiperparámetros; el conjunto de validación se construye a partir de los datos de entrenamiento (no del test), típicamente 80% para entrenar y 20% para validar; la validación estima el error de generalización "during or after training, allowing for the hyperparameters to be updated" — [Deep Learning Book, cap. 5 (deeplearningbook.org)](https://www.deeplearningbook.org/contents/ml.html); contenido verificado vía las diapositivas del curso de S. Srihari que reproducen §5.3: [cedar.buffalo.edu, 5.3 MLBasics-Hyperparam.pdf](https://cedar.buffalo.edu/~srihari/CSE676/5.3%20MLBasics-Hyperparam.pdf)
- Goodfellow et al. (§5.3, vía las mismas diapositivas) sobre benchmarks: cuando el mismo test set se usa durante años para evaluar algoritmos y "beat state-of-the-art performance, we have optimistic evaluations with the test set as well", razón por la cual la comunidad migra a benchmarks nuevos — [Srihari, 5.3 MLBasics-Hyperparam.pdf](https://cedar.buffalo.edu/~srihari/CSE676/5.3%20MLBasics-Hyperparam.pdf)
- **Andrew Ng, *Machine Learning Yearning***: dev set = "data used to make decisions about changes to the model"; test set = "data used to evaluate the model—but *not* to change it, lest we begin to teach our model to the test set" — [Chelsea Troy, Takeaways ML Yearning ch. 1–14](https://chelseatroy.com/2017/06/29/takeaways-machine-learning-yearning-by-andrew-ng-chapters-1-14/)
- Ng: el test set se usa para evaluar el desempeño del algoritmo "but not to make any decisions regarding what learning algorithm or parameters to use"; usarlo para decisiones causa overfitting al test y "the test set can no longer give an unbiased estimate of system performance" — [KDnuggets, 7 Useful Suggestions from ML Yearning](https://www.kdnuggets.com/2018/05/7-useful-suggestions-machine-learning-yearning.html)
- Ng: dev y test deben reflejar la distribución de los datos sobre los que se quiere que el modelo funcione en producción (no necesariamente la del training set) — [KDnuggets](https://www.kdnuggets.com/2018/05/7-useful-suggestions-machine-learning-yearning.html); [Chelsea Troy](https://chelseatroy.com/2017/06/29/takeaways-machine-learning-yearning-by-andrew-ng-chapters-1-14/)
- **scikit-learn (Common pitfalls)**: "Data leakage occurs when information that would not be available at prediction time is used when building the model. This results in overly optimistic performance estimates"; regla general: "never call `fit` on the test data"; "Always split the data into train and test subsets first, particularly before any preprocessing steps"; las transformaciones (escalado, imputación) deben aprenderse solo del train (`fit_transform` en train, `transform` en test), y los Pipelines previenen el leakage — [scikit-learn common pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)

### Inferences
- El consenso entre las cuatro fuentes es estructural, no estilístico: la partición de validación existe *porque* la selección de hiperparámetros es en sí un proceso de ajuste (un "nested learning"), y todo dato usado en cualquier ajuste queda inhabilitado para medir generalización.
- Las proporciones (50/25/25 de ESL; 80/20 train/val de Goodfellow; dev/test "suficientemente grandes para detectar diferencias que importan" de Ng) son heurísticas dependientes del tamaño del dataset, no reglas fijas: todas las fuentes lo dicen explícitamente o lo condicionan.

### Gaps
- No pude recuperar el texto íntegro del PDF de ESL (archivo muy grande para fetch), por lo que las citas de ESL se verificaron a través de fuentes secundarias confiables (Hardt & Recht arXiv:2102.05242, documentación de SAS) más la URL oficial del libro; el fraseo exacto de la cita del "vault" sí está confirmado en arXiv:2102.05242.
- No pude verificar la frase textual exacta del libro de Goodfellow ("It is important that the test examples are not used in any way…"); la paráfrasis citada proviene de diapositivas académicas que reproducen §5.3.

## Protocolos de Raschka (arXiv:1811.12808): holdout, k-fold CV, nested CV por tamaño de dataset y propósito

### Takeaway
Raschka prescribe: holdout de tres vías para datasets grandes (barato computacionalmente), k-fold CV (k=10 como default empírico) para selección de modelos con datos moderados/pequeños, y nested CV para comparar algoritmos con datasets pequeños; tras seleccionar, re-entrenar con train+validación combinados.

### Cited Findings
- El método holdout simple "is not recommended when working with small datasets" — [Raschka, arXiv:1811.12808 (abstract)](https://arxiv.org/abs/1811.12808)
- Holdout de tres vías: "we split the dataset into three parts, a training set for model fitting, a validation set for model selection, and a test set for the final evaluation"; para datasets grandes "the three-way holdout may be preferred over k-fold cross-validation since the former is computationally cheap in comparison" y la varianza es menos problemática — [Raschka, arXiv:1811.12808 (texto completo, ar5iv)](https://ar5iv.labs.arxiv.org/html/1811.12808)
- Elección de k: "Kohavi's experiments on various real-world datasets suggest that 10-fold cross-validation offers the best trade-off between bias and variance"; para datasets muy pequeños LOOCV puede preferirse pese a su costo — [Raschka, ar5iv](https://ar5iv.labs.arxiv.org/html/1811.12808)
- Nested cross-validation es lo recomendado "for comparing machine learning algorithms when datasets are small" — [Raschka, arXiv:1811.12808 (abstract)](https://arxiv.org/abs/1811.12808)
- Protocolo de re-entrenamiento: tras la selección, "we can merge the training and validation set after model selection and use the best hyperparameter settings" para ajustar el modelo final con más datos, reduciendo el sesgo pesimista (un modelo entrenado con menos datos "has not reached its capacity yet"), aceptando que el desempeño del modelo re-entrenado queda sin observar directamente hasta el test — [Raschka, ar5iv](https://ar5iv.labs.arxiv.org/html/1811.12808)
- El paper también cubre bootstrap como alternativa para "estimating the uncertainty of performance estimates", tests estadísticos para comparación de algoritmos y estrategias para comparaciones múltiples — [Raschka, arXiv:1811.12808 (abstract)](https://arxiv.org/abs/1811.12808)

### Inferences
- La lógica de Raschka separa tres tareas que suelen confundirse: (1) *model evaluation* (estimar generalización), (2) *model selection* (elegir hiperparámetros), (3) *algorithm selection* (comparar familias de algoritmos); cada tarea exige un protocolo distinto, y el error típico de los practicantes es usar el protocolo de (2) para responder (1).
- Mapa práctico implícito: dataset grande → three-way holdout; dataset moderado/pequeño + selección de hiperparámetros → k-fold CV (k=10) con test set aparte; dataset pequeño + comparación de algoritmos → nested CV.

### Gaps
- El paper no da umbrales numéricos explícitos de qué cuenta como dataset "grande" vs. "pequeño"; la decisión queda a juicio del practicante según varianza observada y costo computacional.

## ¿Qué es el sesgo optimista de reportar el score de validación del modelo ganador (winner's curse) y cuán grande puede ser?

### Takeaway
Al elegir el máximo entre muchos scores de validación ruidosos, el score del ganador confunde mérito real con ruido favorable (sesgo de selección); empíricamente este sesgo puede ser tan grande como las diferencias entre algoritmos (Cawley & Talbot) y, en datasets pequeños, puede hacer parecer fuertemente predictivo a un clasificador que en realidad opera al azar (Varma & Simon).

### Cited Findings
- scikit-learn describe el mecanismo: los hiperparámetros "can be tweaked until the estimator performs optimally", con lo que "knowledge about the test set can 'leak' into the model and evaluation metrics no longer report on generalization performance" — [scikit-learn cross_validation docs](https://scikit-learn.org/stable/modules/cross_validation.html)
- Cawley & Talbot (JMLR 2010): la selección de modelos optimiza numéricamente un criterio (p. ej. k-fold CV) que tiene varianza no despreciable, y esa varianza "introduces the potential for over-fitting in model selection"; demuestran que "the effects of over-fitting in model selection are often of comparable magnitude to differences in performance between learning algorithms, and thus cannot be ignored in empirical evaluation", y que varias prácticas comunes de evaluación "are susceptible to a form of selection bias… and thus are unreliable" — [Cawley & Talbot, JMLR 11(70):2079–2107](https://www.jmlr.org/papers/v11/cawley10a.html)
- Varma & Simon (BMC Bioinformatics 2006), experimento con datasets "nulos" (sin diferencia real entre clases, error verdadero = 50%): "The CV error estimate for the classifier with the optimal parameters was found to be a substantially biased estimate of the true error"; "the CV error estimate for the Shrunken Centroid with the optimal parameters was less than 30% on 18.5% of simulated training data-sets. For SVM with optimal parameters the estimated error rate was less than 30% on 38% of 'null' data-sets. Performance of the optimized classifiers on the independent test set was no better than chance." — [Varma & Simon 2006, DOI 10.1186/1471-2105-7-91 (abstract vía Semantic Scholar)](https://api.semanticscholar.org/graph/v1/paper/DOI:10.1186/1471-2105-7-91?fields=title,abstract); artículo: [BMC Bioinformatics](https://bmcbioinformatics.biomedcentral.com/articles/10.1186/1471-2105-7-91)
- ESL sobre reutilización del test: si se usa repetidamente para elegir, el error de test del modelo final "will underestimate the true test error, sometimes substantially" — [Hardt & Recht, arXiv:2102.05242](https://arxiv.org/pdf/2102.05242)
- Dwork et al. (reusable holdout / adaptive data analysis): "The moment a team modifies their model based on a previously observed holdout score, they create a dependency between the model and the holdout data that invalidates the classic holdout method assumption", lo que puede llevar a overfitting al holdout que sostiene un leaderboard (demostrado con submissions reales de Kaggle); proponen algoritmos con garantías ("reusable holdout", "Ladder") para reutilización válida — [Dwork et al., arXiv:1506.02629](https://arxiv.org/abs/1506.02629); [Google Research blog, The reusable holdout](https://www.research.google/blog/the-reusable-holdout-preserving-validity-in-adaptive-data-analysis/)
- Contrapunto empírico a gran escala — Recht et al. 2019 ("Do ImageNet Classifiers Generalize to ImageNet?"): al construir test sets nuevos encontraron "accuracy drops of 3% – 15% on CIFAR-10 and 11% – 14% on ImageNet", pero "accuracy gains on the original test sets translate to larger gains on the new test sets", concluyendo que "the accuracy drops are not caused by adaptivity, but by the models' inability to generalize to slightly 'harder' images" — es decir, en benchmarks masivos de visión el overfitting adaptativo al test resultó menor de lo temido, aunque la cifra absoluta de accuracy sí era optimista respecto a datos frescos — [Recht et al., arXiv:1902.10811](https://arxiv.org/abs/1902.10811)

### Inferences
- La magnitud del sesgo crece con: (a) número de configuraciones comparadas, (b) varianza del estimador de validación (datasets pequeños, pocas particiones), y (c) grado de adaptividad (cuántas rondas de feedback del mismo set). Varma & Simon (n pequeño, muchas configuraciones) muestran el caso extremo; Recht et al. (test sets de 10k+ ejemplos, feedback indirecto vía leaderboard) muestran el caso benigno.
- Hay una tensión documentada, no una contradicción: la teoría (Dwork, Cawley & Talbot) dice que la reutilización *puede* invalidar la estimación; la evidencia de Recht dice que en la práctica de benchmarks grandes el ranking entre modelos se preserva. Para datasets pequeños tipo biomedicina, la evidencia de Varma & Simon es la relevante.

### Gaps
- No encontré una fórmula cerrada citable para el tamaño esperado del sesgo del ganador en función del número de modelos comparados (existe literatura sobre máximos de gaussianas ~ σ·√(2·ln M), pero no localicé una fuente canónica de ML que la aplique explícitamente a validación; lo omito para no fabricar la atribución).

## ¿Cuándo se requiere nested cross-validation vs. un único test set retenido?

### Takeaway
Nested CV es necesaria cuando los datos son demasiado escasos para permitirse un test set retenido de tamaño útil y a la vez se quiere estimar la generalización de un *procedimiento* que incluye tuning; con datos abundantes, un único test set retenido (tras selección con validación o CV no anidada) es suficiente y mucho más barato.

### Cited Findings
- Varma & Simon, conclusión: "using CV to compute an error estimate for a classifier that has itself been tuned using CV gives a significantly biased estimate of the true error. Proper use of CV… requires that all steps of the algorithm, including classifier parameter tuning, be repeated in each CV loop. A nested CV procedure provides an almost unbiased estimate of the true error." — [Varma & Simon 2006](https://api.semanticscholar.org/graph/v1/paper/DOI:10.1186/1471-2105-7-91?fields=title,abstract)
- Estructura de nested CV según Varma & Simon: "an inner CV loop is used to perform the tuning of the parameters while an outer CV is used to compute an estimate of the error" — [Varma & Simon 2006](https://bmcbioinformatics.biomedcentral.com/articles/10.1186/1471-2105-7-91)
- Raschka: nested CV se recomienda "for comparing machine learning algorithms when datasets are small"; para datasets grandes el three-way holdout es preferible por costo computacional — [Raschka, arXiv:1811.12808](https://arxiv.org/abs/1811.12808); [ar5iv](https://ar5iv.labs.arxiv.org/html/1811.12808)
- scikit-learn: incluso usando CV para la selección, "A test set should still be held out for final evaluation"; la documentación provee el ejemplo comparativo "Nested versus non-nested cross-validation" que ilustra el optimismo de la CV no anidada — [scikit-learn cross_validation docs](https://scikit-learn.org/stable/modules/cross_validation.html); [ejemplo nested vs non-nested CV](https://scikit-learn.org/stable/auto_examples/model_selection/plot_nested_cross_validation_iris.html)
- Cawley & Talbot muestran que las prácticas de evaluación que no separan la selección de la evaluación (p. ej. reportar la CV usada para el tuning) son "unreliable" y discuten métodos para evitar el sesgo (entre ellos, anidar la selección dentro de la evaluación) — [JMLR 11(70)](https://www.jmlr.org/papers/v11/cawley10a.html)

### Inferences
- Regla de decisión sintetizada de las fuentes: (1) ¿Hay datos de sobra? → three-way holdout; el test retenido responde "¿qué tan bueno es el modelo final?". (2) ¿Datos escasos pero solo se quiere seleccionar hiperparámetros? → k-fold CV sobre el bloque train+val, test retenido para la evaluación final. (3) ¿Datos escasos y se quiere reportar el desempeño esperado del pipeline completo (incluido el tuning) o comparar algoritmos? → nested CV, porque un test pequeño tendría demasiada varianza y la CV no anidada está sesgada.
- Nested CV estima la generalización del *procedimiento de modelado* (algoritmo + política de tuning), no de un modelo concreto fijo; para producción se re-entrena el pipeline completo sobre todos los datos — consistente con el protocolo de re-entrenamiento de Raschka.

### Gaps
- Las fuentes no fijan un umbral numérico (n) a partir del cual el test retenido único deja de necesitar nested CV; Goodfellow et al. (§5.3, vía las diapositivas de Srihari) solo señalan que un test pequeño "implies statistical uncertainty around the estimated average test error" que impide afirmar que el algoritmo A supera al B — [Srihari, 5.3 slides](https://cedar.buffalo.edu/~srihari/CSE676/5.3%20MLBasics-Hyperparam.pdf)

## El papel preciso del test set: estimación de generalización del modelo FINAL, por qué no debe participar en ninguna elección, y qué pasa con su validez tras uso repetido

### Takeaway
El test set existe para una sola cosa: dar una estimación insesgada del error de generalización del modelo final ya elegido; cada vez que influye en una decisión deja de ser "futuro no visto" y su estimación se vuelve optimista, degradándose gradualmente con cada reuso adaptativo.

### Cited Findings
- ESL: el test set corresponde a *model assessment* ("having chosen a final model, estimating its prediction error on new data") y debe mantenerse "in a 'vault,' and be brought out only at the end of the data analysis" — [Hardt & Recht, arXiv:2102.05242 citando ESL](https://arxiv.org/pdf/2102.05242); [ESL](https://hastie.su.domains/ElemStatLearn/)
- Ng: test set = "data used to evaluate the model—but *not* to change it, lest we begin to teach our model to the test set"; no usar el test "for any kind of optimization, including manual hyper-parameter optimization" — [Chelsea Troy](https://chelseatroy.com/2017/06/29/takeaways-machine-learning-yearning-by-andrew-ng-chapters-1-14/); [KDnuggets](https://www.kdnuggets.com/2018/05/7-useful-suggestions-machine-learning-yearning.html)
- scikit-learn: la evaluación final en test llega solo "when the experiment seems to be successful"; la regla operativa es "never call `fit` on the test data" y dividir antes de cualquier preprocesamiento — [scikit-learn cross_validation](https://scikit-learn.org/stable/modules/cross_validation.html); [common pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)
- Mecanismo estadístico de la degradación: la garantía del holdout clásico supone que el modelo es independiente de los datos de test; "the moment a team modifies their model based on a previously observed holdout score, they create a dependency between the model and the holdout data that invalidates the classic holdout method assumption" — [Google Research blog / Dwork et al.](https://www.research.google/blog/the-reusable-holdout-preserving-validity-in-adaptive-data-analysis/); [arXiv:1506.02629](https://arxiv.org/abs/1506.02629)
- A escala comunitaria ocurre lo mismo: años de intentos de superar el estado del arte sobre el mismo benchmark producen "optimistic evaluations with the test set as well", y la comunidad migra a benchmarks nuevos — Goodfellow et al. §5.3 — [Srihari, 5.3 slides](https://cedar.buffalo.edu/~srihari/CSE676/5.3%20MLBasics-Hyperparam.pdf)
- Hardt & Recht observan que la prescripción del "vault" "is far from the reality of modern practice", pues los test sets populares acumulan decenas de miles de evaluaciones — [arXiv:2102.05242](https://arxiv.org/pdf/2102.05242)
- Remedio de Ng cuando el dev set se agota (sobreajustado por tantas decisiones): conseguir un dev set fresco, no reciclar el test — [Chelsea Troy](https://chelseatroy.com/2017/06/29/takeaways-machine-learning-yearning-by-andrew-ng-chapters-1-14/)

### Inferences
- La validez del test es un recurso consumible: la primera lectura es (aprox.) insesgada; cada lectura posterior que retroalimenta el desarrollo convierte progresivamente al test en un segundo dev set. De ahí la práctica MLOps de versionar/renovar test sets y de registrar cuántas veces se consulta.
- "No participar en ninguna elección" incluye elecciones indirectas: preprocesamiento ajustado con todos los datos (leakage de sklearn), selección de features antes del split, o decidir cuándo detener el desarrollo mirando el test.

### Gaps
- Ninguna fuente canónica da una "tasa de consumo" cuantitativa general (cuántas lecturas invalidan el test); los límites formales existen solo en el marco de adaptive data analysis (Dwork et al.) y dependen del tamaño del holdout y el número de consultas.

## ¿La decisión terminal de aceptar/rechazar ("¿es suficientemente bueno para publicar/desplegar?") basada en el test viola el protocolo, o es un uso terminal aceptado?

### Takeaway
Las fuentes canónicas tratan la evaluación final sobre el test — incluida la decisión unidireccional de aceptar o no el modelo ya elegido — como el propósito mismo del test set; lo prohibido es la *selección entre alternativas* o cualquier iteración de desarrollo informada por el score de test. El matiz documentado es que si un "rechazo" dispara más desarrollo y una nueva medición sobre el mismo test, eso ya es reuso adaptativo y erosiona la validez.

### Cited Findings
- scikit-learn describe explícitamente el uso terminal como parte del protocolo correcto: "when the experiment seems to be successful, final evaluation can be done on the test set" — la evaluación final (que naturalmente informa si el resultado se acepta) es el paso sancionado — [scikit-learn cross_validation docs](https://scikit-learn.org/stable/modules/cross_validation.html)
- Ng formula la prohibición en términos de decisiones *sobre el modelo*: el test sirve "to evaluate the performance of the algorithm but not to make any decisions regarding what learning algorithm or parameters to use"; es decir, lo vedado es que el test guíe cambios al sistema, no que se lea su valor para juzgarlo — [KDnuggets, ML Yearning](https://www.kdnuggets.com/2018/05/7-useful-suggestions-machine-learning-yearning.html)
- ESL enmarca el test como *assessment* del modelo final ya elegido ("having chosen a final model, estimating its prediction error") y permite sacarlo del "vault" "only at the end of the data analysis" — el final del análisis es precisamente el momento del juicio terminal — [Hardt & Recht, arXiv:2102.05242 citando ESL](https://arxiv.org/pdf/2102.05242)
- Raschka asigna al test exactamente ese rol en el three-way holdout: "a test set for the final evaluation" tras completar la selección con la validación — [Raschka, ar5iv](https://ar5iv.labs.arxiv.org/html/1811.12808)
- El límite del uso terminal lo marca la literatura de adaptive data analysis: la garantía se pierde "the moment a team modifies their model based on a previously observed holdout score" — por tanto un rechazo seguido de más desarrollo y re-medición sobre el mismo test ya no es uso terminal sino reuso adaptativo — [Google Research blog / Dwork et al.](https://www.research.google/blog/the-reusable-holdout-preserving-validity-in-adaptive-data-analysis/)
- Ng advierte la consecuencia de cruzar ese límite: si se usa el test para decidir cambios, se sobreajusta al test y "the test set can no longer give an unbiased estimate of system performance" — [KDnuggets](https://www.kdnuggets.com/2018/05/7-useful-suggestions-machine-learning-yearning.html)

### Inferences
- Síntesis de la distinción: (a) *selección entre alternativas* usando el test (elegir el modelo/hiperparámetros con mejor test score) = violación clara y unánime; (b) *evaluación one-shot del modelo final* y la decisión binaria derivada (reportar/desplegar o no) = el uso previsto del test set — es literalmente "evaluate the model" (Ng) y "final evaluation" (sklearn, Raschka); (c) *zona gris*: un ciclo rechazar→iterar→volver a medir en el mismo test es, en rigor, selección secuencial entre alternativas (la v1 rechazada y la v2) y acumula el mismo sesgo optimista, aunque más lentamente que un grid search sobre el test. La práctica recomendada derivable de Ng/Dwork es renovar o ampliar el test set si el ciclo de rechazo se repite.
- La estimación de test reportada sigue siendo estadísticamente válida para la decisión de gate precisamente porque la decisión es *posterior* y *unidireccional*: no altera el modelo medido ni eligió entre candidatos usando ese dato.

### Gaps
- Ninguna de las fuentes canónicas consultadas discute explícitamente, con ese vocabulario, la semántica del "ship/no-ship gate"; la distinción (a)/(b)/(c) anterior es una síntesis inferida de sus prescripciones (está marcada como inferencia, no como cita). No encontré una fuente que bendiga o condene textualmente la frase "decisión de despliegue basada en el test"; el tratamiento más cercano es el marco de reuso adaptativo de Dwork et al.
