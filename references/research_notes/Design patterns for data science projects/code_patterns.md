# Code-Level Software Design Patterns in Data Science / Machine Learning Code

## Which classic (GoF and related) design patterns appear in ML code and libraries?

### Takeaway
Classic GoF patterns are pervasive in ML libraries, but usually implicitly: scikit-learn's estimator API is a Template Method + Strategy combination, training callbacks (Keras, PyTorch Lightning) are the Observer pattern, data readers are Adapters/Factories, and `Pipeline` is the field's signature composite/chain pattern. Eugene Yan's essay and the scikit-learn API paper are the most citable mappings of GoF patterns onto named library features.

### Cited Findings
- **Pipeline pattern**: scikit-learn's `Pipeline` chains sequential transformations followed by a final estimator; "Being able to chain and vary transforms and estimators makes for convenient pipeline parameter tuning." Spark MLlib pipelines (tokenizers, transformers, estimators) are the same pattern — [Eugene Yan, "Design Patterns in Machine Learning Code and Systems"](https://eugeneyan.com/writing/design-patterns/)
- **Pipeline composition works because of a uniform interface contract**: all sklearn steps share `fit(X, y)`; transformers expose `transform(X)`, predictors expose `predict(X)`, and `get_params`/`set_params` lets `GridSearchCV` tune hyperparameters across all steps without special wiring — [scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html)
- **Template Method + Strategy as the "defining" pattern of sklearn-like toolboxes**: the "scitype template/strategy pattern" (a base class template implements universal interface points; concrete estimators of the same scitype are interchangeable strategies) is described as "the central pattern used in contemporary toolbox architectures" and "defining for scikit-learn-like toolboxes," explicitly traced to Gamma et al.'s (GoF) template and strategy patterns — [Király et al., "Designing Machine Learning Toolboxes: Concepts, Principles and Patterns" (arXiv:2101.04938)](https://arxiv.org/pdf/2101.04938)
- **Strategy**: XGBoost's configurable tree-construction methods and custom objective functions; Hugging Face Transformers pipelines that swap models per task — "depending on the strategy object used, the context behavior can vary at runtime" — [Eugene Yan](https://eugeneyan.com/writing/design-patterns/)
- **Factory**: PyTorch's `Dataset` class for custom data loaders, Gensim's `TextCorpus`, Hugging Face `Dataset` (Arrow-backed). "Creating these objects can sometimes be complex (e.g., distributed data loaders) and providing a base factory helps users by simplifying object creation." — [Eugene Yan](https://eugeneyan.com/writing/design-patterns/); a simpler idiom maps model-type strings to sklearn classes (LogisticRegression, RandomForestClassifier, ...) in a factory function — [KDnuggets, "Python Patterns for Intermediate Data Scientists"](https://www.kdnuggets.com/breaking-out-of-beginner-python-patterns-for-intermediate-data-scientists)
- **Adapter**: pandas' ~20 `read_*` functions (CSV, JSON, Excel...), Spark data-source readers, and Apache Arrow standardizing columnar formats; "Adapters are often used to read data stored in different formats into a standard data object such as a Dataframe." — [Eugene Yan](https://eugeneyan.com/writing/design-patterns/)
- **Decorator**: Python's `@lru_cache` for memoization, `@pytest.fixture` for test data, custom timing decorators — objects are "decorated (adding functionality) at run time without having to update the structure or behavior of other objects" — [Eugene Yan](https://eugeneyan.com/writing/design-patterns/)
- **Iterator**: PyTorch's `DataLoader` (batching, shuffling, collate functions) "decouples the traversal algorithm from the data container" — [Eugene Yan](https://eugeneyan.com/writing/design-patterns/)
- **Observer (training callbacks)**: Keras callbacks are objects that "perform actions at various stages of training" via hooks (`on_epoch_begin/end`, `on_batch_begin/end`, `on_train_begin/end`); ~14 built-ins including `EarlyStopping`, `ModelCheckpoint`, `TensorBoard`, `ReduceLROnPlateau`, `CSVLogger`, `TerminateOnNaN`, passed as a list to `model.fit(callbacks=...)` — [Keras Callbacks API](https://keras.io/api/callbacks/)
- **Observer/hooks in PyTorch Lightning**: hooks "insert custom behavior at specific points during the training process without modifying the core training loop"; implementable in the LightningModule, in Callback classes passed to the Trainer, or in a Strategy; callbacks are called first, in the order passed — [PyTorch Lightning hooks docs](https://lightning.ai/docs/pytorch/latest/common/hooks.html); the `Callback` base class with per-event methods is in the [Lightning source](https://pytorch-lightning.readthedocs.io/en/stable/_modules/pytorch_lightning/callbacks/callback.html)
- **Template Method in sklearn mixins**: `TransformerMixin` provides `fit_transform()` (calls `fit().transform()`), `ClassifierMixin`/`RegressorMixin` provide default `score()` (accuracy / R²) — concrete classes only fill in `fit`/`predict`/`transform` — [scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html)
- **Prototype-like cloning**: sklearn meta-estimators (`GridSearchCV`) use `clone()` to create unfitted copies preserving only constructor arguments, preventing state leakage between trials; customizable via `__sklearn_clone__` — [scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html)
- **Duck typing over inheritance**: sklearn "uses duck typing rather than isinstance() checks"; an estimator need not inherit from sklearn classes to work in a `Pipeline`, though mixins avoid boilerplate — [scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html)
- The sklearn API design paper (Buitinck, Louppe, Blondel, Pedregosa et al., ECML 2013) describes the estimator/predictor/transformer interfaces, duck typing, and composition via `Pipeline` and `FeatureUnion`, and states the design supports "composition and reusability" — [arXiv:1309.0238](https://arxiv.org/abs/1309.0238)
- **Proxy and Mediator at systems level**: cache proxies for frequent inference/search queries, reverse proxies distributing inference load; mediators centralizing communication (e.g., widget-ranking middlemen) — [Eugene Yan](https://eugeneyan.com/writing/design-patterns/)
- A worked example repo applies GoF patterns (incl. creational patterns) specifically to MLflow experiment tracking — [DesignPatterns-MLFlow-for-ExperimentTracking (GitHub)](https://github.com/UribeAlejandro/DesignPatterns-MLFlow-for-ExperimentTracking); an MLOps coding course dedicates a chapter to design patterns for ML codebases — [MLOps Coding Course, ch. 5.0 Design Patterns](https://mlops-coding-course.fmind.dev/5.%20Refining/5.0.%20Design%20Patterns.html)

### Inferences
- The most defensible claims in a write-up: sklearn `Pipeline` = pipeline/composite pattern; `BaseEstimator` + mixins = Template Method; interchangeable estimators sharing `fit`/`predict` = Strategy; Keras/Lightning callbacks = Observer; pandas/Spark readers = Adapter; `Dataset`/`DataLoader` = Factory + Iterator. Each of these has a named, citable source above.
- **Facade and Singleton** are commonly claimed (e.g., `keras.Model.fit` hiding the training loop as a Facade; MLflow's module-level `mlflow.log_metric` with a single active run/tracking client as a Singleton-ish global), but I found no authoritative source explicitly naming them, so treat these as plausible unnamed instances rather than cited facts (see Gaps).
- **Builder** likewise appears in fluent APIs (Spark's `SparkSession.builder`, sklearn `Pipeline` construction helpers like `make_pipeline`), but no fetched source names it as such for ML code.

### Gaps
- No authoritative source found that explicitly labels Facade, Singleton, or Builder in major ML libraries (Eugene Yan's taxonomy omits them); claims about MLflow clients or `SparkSession.builder` as Singleton/Builder would be inference, not citation.
- The Buitinck et al. paper's full list of five principles (consistency, inspection, non-proliferation of classes, composition, sensible defaults) is in the paper body; the abstract fetch confirmed only "composition and reusability" verbatim — the five-principle list is well known but was not verbatim-confirmed in this fetch.

## What DS-specific coding idioms are considered good practice?

### Takeaway
The canonical idioms are: separate configuration from code (Hydra/YAML/pydantic), keep raw data immutable and treat the analysis as a DAG, confine learning to `fit` and reuse via `transform` to prevent leakage (with preprocessing inside a Pipeline under cross-validation), prefer method chaining with `.pipe`/`.assign` over mutation, control randomness explicitly, and graduate repeated notebook code into tested source modules.

### Cited Findings
- **Config-driven code (Hydra)**: Hydra "separates code from configuration, making experiments reproducible and composable," supports hierarchical configs (experiment → data + model specs) and runtime overrides, and integrates with MLflow — [KDnuggets, "Hydra Configs for Deep Learning Experiments"](https://www.kdnuggets.com/2023/03/hydra-configs-deep-learning-experiments.html); combining pydantic validation with Hydra composition for training configs is a documented practice — [Towards Data Science, "Configuration management for model training experiments using pydantic and hydra"](https://towardsdatascience.com/configuration-management-for-model-training-experiments-using-pydantic-and-hydra-d14a6ae84c13)
- **Fit/transform separation to avoid leakage**: "The general rule is to never call fit on the test data"; transformations "are only learnt from the training data... the average should be the average of the train subset, not the average of all the data"; workflow = `fit_transform` on train, `transform` on both — [scikit-learn Common Pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)
- **Preprocessing inside Pipeline under CV**: "The scikit-learn pipeline is a great way to prevent data leakage as it ensures that the appropriate method is performed on the correct data subset." Demonstrated consequence: `SelectKBest` fit on all data before splitting gave 76% accuracy on *random* targets vs the correct 50% when fit on train only — [scikit-learn Common Pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)
- **Controlling randomness**: declare RNG explicitly (`rng = np.random.RandomState(0)`) for reproducibility ("We are now guaranteed that the result of this script will always be 0.84"); pass integers to CV splitters, RandomState instances to estimators for fairer algorithm comparison — [scikit-learn Common Pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)
- **Raw data immutability + DAG structure**: "Raw data must be treated as immutable — it's okay to read and copy raw data to manipulate it into new outputs, but never okay to change it in place"; organize analysis as a DAG with no circular dependencies so outputs can be recreated forward or traced backward — [Cookiecutter Data Science, Opinions](https://cookiecutter-data-science.drivendata.org/opinions/)
- **Notebooks for exploration, source for repetition**: "Source code is superior for replicability because it is more portable, can be tested more easily, and is easier to code review"; repetitive/shared tasks should migrate from notebooks to source files — [Cookiecutter Data Science, Opinions](https://cookiecutter-data-science.drivendata.org/opinions/)
- **Secrets and paths**: store credentials in `.env` excluded from version control, loaded with python-dotenv; reproduce the computational environment first (conda/Docker) — [Cookiecutter Data Science, Opinions](https://cookiecutter-data-science.drivendata.org/opinions/)
- **Method chaining on DataFrames**: pandas `.assign` (added 0.16.0, inspired by dplyr `mutate`) and `.pipe` (0.16.2, lets user functions join a chain "without monkeypatching") present transformations top-to-bottom mirroring execution flow; author argues against intermediate variables ("I have to spend time coming up with appropriate names for variables") and against `inplace=True` (returns None, breaks chaining, no memory guarantee) — [Tom Augspurger, "Method Chaining" (Modern Pandas)](https://tomaugspurger.net/posts/method-chaining/)
- **Chaining's known cost**: debugging — long chains hide intermediate values; for substantial workflows Augspurger recommends graduating to orchestrators (Airflow/Luigi) — [Tom Augspurger](https://tomaugspurger.net/posts/method-chaining/)
- **Modular script layout**: Made With ML (Goku Mohandas) refactors notebook code into `config.py`, `data.py`, `models.py`, `train.py`, `evaluate.py`, `predict.py`, `tune.py`, `serve.py`, `utils.py`; rationale: "scripts are stateless, requiring explicit variable passing," execute linearly rather than by cell order, and are far easier to test — [Made With ML, MLOps course: Scripting](https://madewithml.com/courses/mlops/scripting/)
- **sklearn constructor discipline as an idiom worth copying**: constructors must only store parameters unchanged (no validation, no mutation, no data-derived defaults) — logic belongs in `fit()`; every `__init__` kwarg stored as a same-named attribute; learned attributes get a trailing underscore (`coef_`), internal state a leading underscore — [scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html)
- sklearn's stated rationale: consistency ("uniform API across 200+ estimators enables switching algorithms with one-line changes"), sensible defaults, no hidden state, reproducibility — [scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html)

### Inferences
- "Pure functions for feature engineering" and "separate I/O from transformation logic" are directly implied by three cited sources converging: Cookiecutter's immutable-data/DAG opinion, Augspurger's chain-of-transformations style, and Made With ML's stateless-scripts argument — but no single source states the phrase "pure functions for feature engineering" verbatim.
- The sklearn constructor rule (store params, defer work to `fit`) is effectively the DS version of "no work in constructors" from general clean-code literature, and is what makes grid search, cloning, and pipelines composable.

### Gaps
- No fetched source explicitly frames "separate I/O from transformation" as a named principle (it is folklore distilled from the sources above).
- Did not verify a specific "Effective Python"/"Clean Code in Python" chapter applied to DS; no citable DS-specific mapping of those books was found in this research pass.

## What anti-patterns are commonly called out in DS code?

### Takeaway
The canonical critiques cluster around notebooks (hidden state, out-of-order execution, copy-paste duplication, untestability, unreviewable diffs) and system-level debt (glue code, entanglement, configuration debt) named in Google's "Hidden Technical Debt" paper — the single most cited anti-pattern source in ML.

### Cited Findings
- **The Notebook Anti-Pattern** (Kristina Young, BCG Digital Ventures): notebooks foster (1) reliance on notebook-wide mutable state changing with each cell execution; (2) code duplication because notebooks can't be imported into each other; (3) lack of testing; (4) unreadable pull requests / poor version control; (5) merge-conflict-prone collaboration; (6) manual dependency tracking. Recommendation: notebooks only for experimentation/analysis; "Stick to software engineering principles and frameworks for bringing things to production." — [KDnuggets, "The Notebook Anti-Pattern"](https://www.kdnuggets.com/2019/11/notebook-anti-pattern.html)
- **Hidden Technical Debt in ML Systems** (Sculley et al., NeurIPS 2015) names: boundary erosion, entanglement (CACE — changing anything changes everything), hidden feedback loops, undeclared consumers, fragile data dependencies, configuration debt, and degradation from external-world change, framed as "massive ongoing maintenance costs" — [NeurIPS 2015 abstract](https://proceedings.neurips.cc/paper/2015/hash/86df7dcfd896fcaf2674f757a2463eba-Abstract.html). (Glue code, pipeline jungles, dead experimental codepaths, and abstraction debt are in the full paper body; the abstract fetch confirmed the list above only.)
- Academic consensus: bad practices in ML notebooks arise at three levels — general Python conventions, notebook organizational structure, and ML-specific aspects (reproducibility, correct API usage); "ML code often shows lower quality than traditional software" and notebooks "lack rigorous enforcement of coding standards due to limited integration with linters or code-smell detectors" — [arXiv:2509.11748 (notebook quality study)](https://arxiv.org/html/2509.11748v1); the notebook format "has been criticized for inducing bad programming practices... which constitutes a bottleneck towards productizing ML models" — [Pynblint: a Static Analyzer for Python Jupyter Notebooks](https://paperswithcode.com/paper/pynblint-a-static-analyzer-for-python-jupyter)
- Made With ML's stated reasons to leave notebooks mirror the anti-patterns: notebooks save everything to global state and depend on cell execution order; scripts are stateless and testable — [Made With ML, Scripting](https://madewithml.com/courses/mlops/scripting/)
- Hardcoded paths / leaked secrets are called out implicitly by Cookiecutter DS's rules (secrets in `.env` out of version control; environment reproducibility first) — [Cookiecutter Data Science, Opinions](https://cookiecutter-data-science.drivendata.org/opinions/)
- Leakage as an anti-pattern has a dedicated upstream doc: fitting preprocessing on the full dataset before splitting "results in overly optimistic performance estimates" (76% accuracy on random labels example) — [scikit-learn Common Pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)
- `inplace=True` mutation on DataFrames is called out as an anti-idiom: it returns None, breaks chaining, and does not guarantee memory savings — [Tom Augspurger](https://tomaugspurger.net/posts/method-chaining/)

### Inferences
- The popular shorthand "it works in my notebook" is a community phrase summarizing Young's state-reliance + untestability critique; no single canonical source coins it.
- Combined, the anti-pattern canon is: notebook spaghetti (hidden state, order dependence, copy-paste cells), hardcoded paths/secrets, global mutable state, uncontrolled randomness, leakage from pre-split preprocessing, and (system-level) glue code/configuration debt.

### Gaps
- Could not verify a specific neptune.ai blog post on ML code anti-patterns in this pass; searches surfaced academic and KDnuggets sources instead. The neptune.ai blog does cover MLOps practice, but no specific URL was confirmed, so neptune.ai should not be cited for anti-patterns without further checking.
- The full Sculley et al. anti-pattern list (glue code, pipeline jungles, dead experimental codepaths, abstraction debt) was only confirmable from the abstract page at the headline level; citing the detailed items should reference the full PDF.
- Martin Fowler's CD4ML article was not fetched in this pass; no citable detail gathered.

## What do well-known references say (ML Design Patterns book; practitioner sources)?

### Takeaway
"Machine Learning Design Patterns" (Lakshmanan, Robinson, Munn, O'Reilly 2020) catalogs 30 patterns, but most are ML-architecture patterns rather than GoF-style code patterns; only a handful (Transform, Workflow Pipeline, Checkpoints, Stateless Serving Function) prescribe code-level structure. The best code-level references are Eugene Yan's design-patterns essay, the scikit-learn API paper/developer docs, and Made With ML's MLOps course.

### Cited Findings
- The book, by three Google engineers (published Oct 2020), contains "detailed explanations of 30 patterns for data and problem representation, operationalization, repeatability, reproducibility, flexibility, explainability, and fairness"; each pattern gives problem, solutions, and selection recommendations — [O'Reilly book page](https://www.oreilly.com/library/view/machine-learning-design/9781098115777/); also listed as a Google Research publication — [research.google](https://research.google/pubs/machine-learning-design-patterns/)
- Full pattern list by chapter (from the authors' companion repo): **Data Representation**: Hashed Feature, Embedding, Feature Cross, Multimodal Input. **Problem Representation**: Reframing, Multilabel, Ensemble, Cascade, Neutral Class, Rebalancing. **Model Training**: Useful Overfitting, Checkpoints, Transfer Learning, Distribution Strategy, Hyperparameter Tuning. **Resilience**: Stateless Serving Function, Batch Serving, Continuous Model Evaluation, Two-Phase Predictions, Keyed Predictions. **Reproducibility**: Transform, Repeatable Sampling, Bridged Schema, Windowed Inference, Workflow Pipeline, Feature Store, Model Versioning. **Responsible AI**: Heuristic Benchmark, Explainable Predictions, Fairness Lens — [GoogleCloudPlatform/ml-design-patterns (GitHub)](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- Eugene Yan (applied scientist at Amazon, known for production-ML writing) maps Factory, Adapter, Decorator, Strategy, Iterator, Pipeline, Proxy, Mediator onto concrete library features (see Q1 for the full mapping) — [eugeneyan.com](https://eugeneyan.com/writing/design-patterns/)
- Made With ML (Goku Mohandas) teaches the notebook→scripts refactor with a canonical module layout and reasons (statelessness, linear execution, testability), and that clean scripts should carry "testing, documentation, logging, serving, versioning" — [madewithml.com MLOps course](https://madewithml.com/courses/mlops/scripting/)
- The sktime-adjacent academic treatment, "Designing Machine Learning Toolboxes" (Király et al.), is the most formal source tying GoF template/strategy patterns to the sklearn estimator architecture — [arXiv:2101.04938](https://arxiv.org/pdf/2101.04938)
- scikit-learn's own developer guide is the primary source for the estimator contract (constructor discipline, `get_params`/`set_params`, mixins, trailing-underscore learned attributes, cloning, duck typing) — [scikit-learn developer docs](https://scikit-learn.org/stable/developers/develop.html); its academic counterpart is [Buitinck et al., arXiv:1309.0238](https://arxiv.org/abs/1309.0238)
- Cookiecutter Data Science (DrivenData) is the standard citable source for project-structure opinions (immutable raw data, DAG, notebooks-vs-source, secrets, environments) — [Opinions page](https://cookiecutter-data-science.drivendata.org/opinions/)
- The Sculley et al. NeurIPS 2015 paper is the standard citation for ML technical debt / anti-patterns — [NeurIPS proceedings](https://proceedings.neurips.cc/paper/2015/hash/86df7dcfd896fcaf2674f757a2463eba-Abstract.html)

### Inferences
- **Which of the book's 30 patterns are code-level** (inference from the pattern list; the book does not label them this way): *Transform* (capture train-time transformations so serving applies identical code — the book's version of fit/transform separation), *Workflow Pipeline* (containerized, step-decomposed pipeline code), *Checkpoints* (training-loop code structure), *Stateless Serving Function* (export model as a pure function), and arguably *Repeatable Sampling* (hash-based splits in code) and *Keyed Predictions*. The remainder (Embeddings, Feature Cross, Reframing, Ensembles, Cascade, Feature Store, Fairness Lens, etc.) are data/problem/architecture patterns, not code-structure patterns.
- For a course or write-up, the cleanest citation strategy is: GoF-pattern claims → Eugene Yan + Király et al.; estimator API claims → sklearn dev docs + Buitinck et al.; callbacks → Keras/Lightning docs; idioms → Cookiecutter DS + sklearn Common Pitfalls + Augspurger; anti-patterns → Young (KDnuggets) + Sculley et al.

### Gaps
- The book itself was not directly readable; which patterns are "code-level" is my classification, not the authors'. The chapter/pattern list from the companion GitHub repo is authoritative, though.
- No confirmed citable material from neptune.ai or Martin Fowler's CD4ML in this pass (see previous section's gaps).
- "Clean Code in Python"/"Effective Python" applied specifically to DS: no named, citable source found connecting these books to DS idioms.
