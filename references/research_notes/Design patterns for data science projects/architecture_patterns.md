# System Architecture Design Patterns for Machine Learning Systems

Dense notes on named, well-known architecture patterns for ML systems at the pipeline/serving/data level, with canonical sources. Compiled 2026-10-11.

## Key Question 1: What patterns does the O'Reilly book "Machine Learning Design Patterns" (Lakshmanan, Robinson, Munn, 2020) catalog?

### Takeaway
The book catalogs 30 named patterns written by three Google engineers (Valliappa Lakshmanan, Sara Robinson, Michael Munn; O'Reilly, Oct 2020), organized into six categories: Data Representation (4), Problem Representation (6), Model Training (5), Resilient Serving (5), Reproducibility (7), and Responsible AI (3). The authors' official companion repository (GoogleCloudPlatform/ml-design-patterns) confirms the full list.

### Cited Findings
- The book "Machine Learning Design Patterns: Solutions to Common Challenges in Data Preparation, Model Building, and MLOps" contains 30 patterns covering data/problem representation, operationalization, repeatability, reproducibility, flexibility, explainability, and fairness; authors are Google engineers Lakshmanan, Robinson, and Munn (O'Reilly, 2020) — [O'Reilly book page](https://www.oreilly.com/library/view/machine-learning-design/9781098115777/); also listed as a Google Research publication — [research.google](https://research.google/pubs/machine-learning-design-patterns/)
- Full catalog confirmed by the authors' official companion repository — [GoogleCloudPlatform/ml-design-patterns (GitHub)](https://github.com/GoogleCloudPlatform/ml-design-patterns):

**Ch.2 — Data Representation (patterns 1–4)**
- **Hashed Feature**: bucket categorical variables via a deterministic hash into a fixed-size vector; handles incomplete vocabularies, high cardinality, and cold start — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Embeddings**: learn dense, low-dimensional vector representations of sparse/high-cardinality features — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Feature Cross**: explicitly create interaction features from combinations of input features so simple models can learn nonlinear relationships — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Multimodal Input**: combine heterogeneous data types (text + image + tabular) as input to one model — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)

**Ch.3 — Problem Representation (patterns 5–10)**
- **Reframing**: reformulate the task (e.g., regression as classification or vice versa) for better output distributions — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Multilabel**: handle examples that can belong to multiple classes simultaneously (sigmoid outputs instead of softmax) — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Ensembles**: combine predictions of multiple models (bagging/boosting/stacking) to reduce bias/variance — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Cascade**: split an unusual/compound problem into a series of models where downstream models consume upstream predictions; treat the whole cascade as one workflow — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Neutral Class**: add an explicit "neither/uncertain" class for cases where labels are arbitrary or ambiguous — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Rebalancing**: handle skewed class distributions with downsampling/upsampling/weighting — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)

**Ch.4 — Model Training (patterns 11–15)**
- **Useful Overfitting**: deliberately overfit (no regularization/val set) when the goal is to memorize a complete deterministic input space, e.g., approximating physics simulations — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Checkpoints**: periodically save full model state during training to resume after failures, support early stopping and fine-tuning — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Transfer Learning**: reuse a pre-trained model's learned representations; fine-tune on the target task with less data — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Distribution Strategy**: distribute training across multiple devices/machines (data parallelism sync/async, model parallelism) — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Hyperparameter Tuning**: treat hyperparameter search as an outer optimization loop (grid/random/Bayesian) — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)

**Ch.5 — Resilient Serving (patterns 16–20)**
- **Stateless Serving Function**: export the model as a stateless function so serving can autoscale across many independent workers (basis of REST model endpoints) — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Batch Serving**: use distributed data-processing infrastructure to run inference asynchronously over large datasets when predictions are not needed immediately — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Continued Model Evaluation** (repo spelling: "Continuous Model Evaluation"): keep evaluating deployed-model performance on fresh labeled data to detect staleness/drift and trigger retraining — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Two-Phase Predictions**: split the problem into a small/cheap model (e.g., on-device/edge) that gates a larger, more precise model (e.g., in the cloud) — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Keyed Predictions**: pass a client-supplied key through with each instance so asynchronous/distributed batch outputs can be joined back to inputs — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)

**Ch.6 — Reproducibility (patterns 21–27)**
- **Transform**: explicitly separate inputs, features, and transforms, persisting the transformations, so the exact same transformation code is applied at training and serving time ("the Transform pattern enforces the separation of inputs, features, and transforms and making the transformations persistent in order to simplify moving an ML model to production") — [O'Reilly book page](https://www.oreilly.com/library/view/machine-learning-design/9781098115777/)
- **Repeatable Splitting** (repo: "Repeatable Sampling"): use a deterministic hash of a well-chosen column (e.g., FARM_FINGERPRINT) to split data into train/valid/test so splits are reproducible and leakage-free — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Bridged Schema**: adapt training data from an older schema to match a newer one so old and new data can be combined — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Windowed Inference**: externalize model state and run features over time windows so dynamic, time-windowed features are computed identically in training and serving — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Workflow Pipeline**: containerize and orchestrate every step of the ML workflow (data prep, training, evaluation, deployment) as a DAG (e.g., Kubeflow/TFX pipelines) for reproducibility — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Feature Store**: a centralized repository to store, document, and serve features consistently across teams and across training/serving — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Model Versioning**: deploy changed models as versioned endpoints (new version or new model) so consumers can pin versions and teams can run backward-compatible updates and A/B comparisons — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)

**Ch.7 — Responsible AI (patterns 28–30)**
- **Heuristic Benchmark**: compare the model against a simple, explainable heuristic baseline to communicate its value — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Explainable Predictions**: apply feature-attribution/interpretability techniques (e.g., SHAP, Integrated Gradients) to explain model outputs — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Fairness Lens**: evaluate data and model behavior across slices/groups to identify and mitigate bias before and after training — [GitHub repo](https://github.com/GoogleCloudPlatform/ml-design-patterns)

### Inferences
- The task brief's list of ~28 patterns omitted **Windowed Inference** (pattern 24, Reproducibility); the authors' repo confirms the Reproducibility chapter has 7 patterns, giving the canonical total of 30.
- Minor naming variants exist between the book chapters and the companion repo ("Repeatable Splitting" vs "Repeatable Sampling"; "Continued" vs "Continuous" Model Evaluation); both refer to the same patterns.

### Gaps
- Per-pattern "when to use" trade-off discussion in the book's full depth is behind the O'Reilly paywall; the one-line definitions above are from the authors' public repo and publisher page, not full chapter text.

## Key Question 2: What serving/deployment architecture patterns are standard (batch/online/streaming inference, model-as-service, embedded model, shadow, champion/challenger, canary, A/B, serverless)?

### Takeaway
Industry practice converges on three inference modes (batch, online/synchronous, streaming/asynchronous) and three packaging modes (embedded model, model-as-a-service, model-as-data, per Thoughtworks CD4ML), combined with progressive-rollout patterns (shadow → canary → A/B / champion-challenger). The most complete open catalog of named serving patterns is Mercari's ml-system-design-pattern repo.

### Cited Findings
- **CD4ML model serving patterns** (Sato, Wider, Windheuser, Thoughtworks, on martinfowler.com): **Embedded Model** = model packaged inside the consuming application as a build dependency; **Model as a Service** = model wrapped in an independently deployed service (REST/gRPC endpoint) so it can be updated separately; **Model as Data** = model published as data and ingested at runtime by consumers, enabling blue-green or canary deployments — [martinfowler.com/articles/cd4ml.html](https://martinfowler.com/articles/cd4ml.html)
- CD4ML definition: "a software engineering approach in which a cross-functional team produces machine learning applications based on code, data, and models in small and safe increments that can be reproduced and reliably released at any time, in short adaptation cycles" — [martinfowler.com/articles/cd4ml.html](https://martinfowler.com/articles/cd4ml.html)
- **Mercari serving patterns catalog**: Web single, Synchronous, Asynchronous, Batch, Prep-pred (separate preprocessing and prediction services), Microservice vertical, Microservice horizontal, Prediction cache, Data cache, Prediction circuit break (fallback on failure), Multiple stage prediction, Serving template; QA patterns: Shadow AB-testing (evaluate a model on live traffic without affecting responses), Online AB-testing, Loading test; serving anti-patterns: Online bigsize (oversized model in a latency-critical path), All-in-one (monolith) — [mercari/ml-system-design-pattern (GitHub)](https://github.com/mercari/ml-system-design-pattern)
- Mercari operation patterns relevant to deployment: Model-in-image (model baked into the container image) vs Model-load (model loaded dynamically at runtime), Parameter-based serving and Condition-based serving (routing by config/condition), Prediction log, Prediction monitoring — [mercari/ml-system-design-pattern](https://github.com/mercari/ml-system-design-pattern)
- **Batch vs online prediction** (Chip Huyen): batch prediction precomputes predictions at intervals and stores them (e.g., recommendations regenerated periodically), wasting compute on inactive users and failing for new visitors; online prediction generates predictions on request (REST APIs), optionally using precomputed batch features; "Batch prediction is NOT a prerequisite for online prediction" — a legacy assumption from the MapReduce/Spark era — [huyenchip.com, Real-time ML: challenges and solutions](https://huyenchip.com/2022/01/02/real-time-machine-learning-challenges-and-solutions.html)
- **Online prediction with streaming features**: combine batch features with real-time features (computed at request time, millisecond-fresh, latency-sensitive) or near-real-time features (precomputed asynchronously by a stream processor, seconds-stale); requires streaming transport (Kafka/Kinesis), a stream computation engine (Flink/KSQL), a feature store, and a model store — [huyenchip.com](https://huyenchip.com/2022/01/02/real-time-machine-learning-challenges-and-solutions.html)
- **Shadow deployment**: a new (challenger) model receives a copy of production traffic in parallel with the live champion; its outputs are logged and compared offline but never served to users — zero user risk — [Atlan: Shadow deployment for ML models](https://atlan.com/know/shadow-deployment-for-ml-models/); [MetricGate: Shadow deployment vs canary rollout](https://metricgate.com/blogs/shadow-deployment-vs-canary/)
- **Canary rollout**: serve the new model to a small slice of real traffic (typically 1–5%) and progressively expand; a typical safe progression is shadow mode → 1–5% canary → larger splits — [MetricGate](https://metricgate.com/blogs/shadow-deployment-vs-canary/)
- **Champion/challenger**: a proven production model (champion) is continuously compared against one or more candidate models (challengers) on accuracy/latency; multiple challengers can run against one champion — [SecurityScientist: champion-challenger models](https://www.securityscientist.net/blog/12-questions-and-answers-about-champion-challenger-models/); [MetricGate](https://metricgate.com/blogs/shadow-deployment-vs-canary/)
- **Online A/B testing**: split live user traffic between models and compare business/quality metrics; cataloged as a distinct QA pattern from shadow testing (which does not affect responses); anti-pattern: Offline-only (never validating with real traffic) — [mercari/ml-system-design-pattern](https://github.com/mercari/ml-system-design-pattern)
- The book's **Stateless Serving Function** pattern is the architectural basis for autoscaled model-as-service REST endpoints, and **Two-Phase Predictions** is the canonical edge+cloud split (small on-device model gates calls to a large cloud model) — [GoogleCloudPlatform/ml-design-patterns](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Model Versioning** pattern: deploying each model change as a versioned endpoint enables backward compatibility and A/B comparison between versions — [GoogleCloudPlatform/ml-design-patterns](https://github.com/GoogleCloudPlatform/ml-design-patterns)

### Inferences
- The patterns compose into a standard progressive-delivery ladder for ML: offline evaluation → shadow (0% user impact) → canary (1–5%) → A/B test (statistical comparison) → full rollout, with champion/challenger as the ongoing steady-state comparison regime.
- "Serverless inference" is best understood as an infrastructure realization of the Stateless Serving Function pattern (scale-to-zero FaaS/managed endpoints) rather than an independent design pattern.

### Gaps
- I did not fetch a canonical first-party cloud-vendor page (AWS SageMaker / Azure ML) defining "serverless inference" as a named pattern; a Databricks community thread notes Azure model-serving traffic configuration does not natively support shadow mode ([Databricks community](https://community.databricks.com/t5/machine-learning/model-serving-shadow-deployment-azure/m-p/68066)), but I found no authoritative Azure Architecture Center page in this pass.

## Key Question 3: What data/training architecture patterns are standard (training-serving skew prevention, feature store, lambda/kappa, retraining pipelines, model registry)?

### Takeaway
Google's MLOps reference architecture names the canonical data/training components — automated training pipeline, continuous training, feature store, model registry, metadata store, data/model validation — all aimed chiefly at reproducibility and preventing training-serving skew; lambda (Marz) and kappa (Kreps) architectures are the underlying data-platform patterns that determine whether features are computed in dual batch+speed paths or a single streaming path.

### Cited Findings
- **MLOps maturity levels** (Google Cloud): Level 0 = fully manual, script-driven, handoff from data scientists to engineers, infrequent releases, no CI/CD; Level 1 = ML pipeline automation with continuous training, the same pipeline used in dev and prod, automated data and model validation gates; Level 2 = full CI/CD where source changes automatically test, build, and deploy pipelines — [Google Cloud: MLOps continuous delivery and automation pipelines](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- **Training pipeline**: orchestrated sequence automating data extraction, preparation, training, and evaluation, deployed to production so retraining can be repeated — [Google Cloud MLOps](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- **Continuous training (CT)**: automatic retraining triggered by schedule, new data availability, performance degradation, or data-distribution shift — [Google Cloud MLOps](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- **Feature store**: "centralized repository" standardizing feature definitions, storage, and access for both training and serving, preventing training-serving skew — [Google Cloud MLOps](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning); also pattern 26 of the ML Design Patterns book — [GoogleCloudPlatform/ml-design-patterns](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Model registry**: central repository of trained models plus metadata enabling version control and promotion of validated models to prediction services — [Google Cloud MLOps](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- **Metadata store**: records each pipeline execution's component versions, parameters, artifact locations, and metrics for reproducibility and debugging — [Google Cloud MLOps](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- **Training-serving skew**: inconsistency when production features differ from training features, often from the "disconnection between ML and operations" of Level 0; mitigations include data validation (schema + distribution checks before training) and model validation (compare new model vs production baseline before promotion) — [Google Cloud MLOps](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Skew-prevention rules in Rules of ML: Rule #29 "log the features used at serving time and pipe them to training"; Rule #32 reuse code between training and serving pipelines; Rule #31 beware that data in joined tables can change between training and serving; Rule #37 measure the performance gap across training/holdout/next-day/live data — [developers.google.com Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)
- The book's **Transform** pattern (persist and share transformation logic between training and serving) and **Windowed Inference** pattern (identical time-window feature computation in both phases) are the book's named skew-prevention mechanisms — [O'Reilly](https://www.oreilly.com/library/view/machine-learning-design/9781098115777/); [GoogleCloudPlatform/ml-design-patterns](https://github.com/GoogleCloudPlatform/ml-design-patterns)
- **Lambda architecture** (Nathan Marz, creator of Apache Storm): three layers — batch layer (manages historical data, recomputes results such as ML models over the full dataset), speed layer (low-latency incremental updates), serving layer; main drawback is implementing every computation twice (batch + streaming) — [Ericsson: data processing architectures lambda and kappa](https://www.ericsson.com/en/blog/2015/11/data-processing-architectures--lambda-and-kappa)
- **Kappa architecture** (Jay Kreps, LinkedIn, 2014): treat all data as a stream appended to an immutable log (e.g., Kafka topic); a single stream-processing engine updates derived views and can update ML models on the fly; recomputation = replay the log; eliminates the duplicated batch/speed code of lambda — [Ericsson](https://www.ericsson.com/en/blog/2015/11/data-processing-architectures--lambda-and-kappa); [Materialize: when kappa is most effective](https://materialize.com/blog/when-is-kappa-architecture-most-effective/)
- **Model update/retraining stages** (Chip Huyen): (1) manual ad-hoc retraining, (2) automated scheduled batch retraining (stateless, from scratch), (3) automated stateful training (continue from previous checkpoint; one company "reduced training cost 45 times"), (4) continual learning triggered by drift/performance drops; fixed retraining schedules without drift monitoring are an anti-pattern — [huyenchip.com](https://huyenchip.com/2022/01/02/real-time-machine-learning-challenges-and-solutions.html)
- Mercari training patterns: Batch training (scheduled retraining), Pipeline training (multi-stage automated workflow), Parameter and architecture search; training anti-patterns: Only-me (single-person ownership), Training code in serving, Too many pipes — [mercari/ml-system-design-pattern](https://github.com/mercari/ml-system-design-pattern)
- Data/model versioning in practice: dataset changes tracked via checksums/metadata with tools like DVC; experiments tracked with MLflow Tracking; reproducible training pipelines with DVC, Pachyderm, or MLflow Projects — [martinfowler.com/articles/cd4ml.html](https://martinfowler.com/articles/cd4ml.html); Mercari also names a "Data model versioning" operation pattern — [mercari/ml-system-design-pattern](https://github.com/mercari/ml-system-design-pattern)

### Inferences
- Feature store + Transform + feature logging (Rule #29) are three complementary mechanisms for the same goal (skew prevention): share the data, share the code, or verify via logged serving features.
- Kappa-style architectures are what make Huyen's "online prediction with streaming features" tier practical, since features need a single consistent computation path for both backfill (training) and live serving.

### Gaps
- I found no single authoritative source that explicitly frames "lambda/kappa applied to ML feature engineering" as a named ML pattern; the connection is well-established practice but synthesized here from general lambda/kappa sources plus Huyen's streaming-features architecture.

## Key Question 4: What do Rules of ML (Zinkevich), Hidden Technical Debt (Sculley et al. 2015), and Chip Huyen say about recurring design structures and anti-patterns?

### Takeaway
Sculley et al. (NeurIPS 2015) supplies the canonical ML anti-pattern vocabulary — CACE/entanglement, correction cascades, undeclared consumers, data-dependency debt, hidden feedback loops, glue code (a mature system can be ~5% ML code, 95% glue), pipeline jungles, dead experimental codepaths, configuration debt. Zinkevich's Rules of ML prescribes the positive structures: heuristics first, simple model + solid pipeline, test infrastructure, log serving features, and phase-based evolution.

### Cited Findings
**Hidden Technical Debt in Machine Learning Systems (Sculley et al., NeurIPS 2015)**
- Thesis: ML's quick wins carry massive ongoing maintenance costs, analyzed through a technical-debt framework; risk factors include boundary erosion, entanglement, hidden feedback loops, undeclared consumers, data dependencies, configuration issues, changes in the external world, and system-level anti-patterns — [NeurIPS 2015 paper (PDF)](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- **Entanglement / CACE**: ML systems entangle signals so "Changing Anything Changes Everything" — no input feature is ever truly independent, so isolated improvements are impossible — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- **Correction cascades**: a model trained to correct errors of another model (m'ₐ learned on top of mₐ) creates a system dependency where improving the base model can degrade the corrector, locking in cascading coupling — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- **Undeclared consumers**: external systems silently consume model outputs without contracts; model updates then cause unseen cascading failures (also a hidden feedback risk) — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- **Data dependencies**: unstable or underutilized input signals "cost more than code dependencies"; models degrade silently when upstream data changes without versioning/monitoring of data contracts — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- **Hidden feedback loops**: the system's outputs feed back into its own future training data (directly or via another system), creating uncontrolled dynamics — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- **Glue code**: wrapping general-purpose ML packages in custom connective code; "a mature system might end up being (at most) 5% machine learning code and (at least) 95% glue code" — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf); summarized in [the morning paper (Adrian Colyer)](https://blog.acolyer.org/2016/02/29/machine-learning-the-high-interest-credit-card-of-technical-debt/)
- **Pipeline jungles**: data-preparation pipelines degrade into a jungle of scrapes, joins, samples, and intermediate outputs as new signals are added incrementally; detectable only via expensive end-to-end tests; remedy is holistic redesign of data collection — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- **Dead experimental codepaths**: conditional experimental branches accumulate in production code, exploding cyclomatic complexity and testing burden — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- **Abstraction debt** and **configuration debt**: lack of strong abstractions for ML components, and sprawling unvalidated configuration (features, data selection, hyperparameters) that often exceeds the model code in line count — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- Mitigations recommended: explicit data versioning and schema documentation, input/output monitoring, clear interfaces between ML and production systems, and systematic consolidation of pipelines — [NeurIPS 2015 PDF](https://proceedings.neurips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)

**Rules of ML (Martin Zinkevich, Google)**
- Structured in three phases: Phase I — build the first pipeline with a simple model and solid infrastructure; Phase II — feature engineering and rapid iteration; Phase III — slowed growth and refined optimization — [developers.google.com/machine-learning/guides/rules-of-ml](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Rule #1: don't be afraid to launch a product without ML (use heuristics if data is lacking); Rule #3: choose ML over a complex heuristic; Rule #7: turn existing heuristics into features rather than discarding them — [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Rule #4: "keep the first model simple and get the infrastructure right"; Rule #5: test infrastructure independently of the ML — [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Skew prevention: Rule #29 (log serving-time features for training), Rule #31 (joined-table data can change between training and serving), Rule #32 (reuse code between training and serving pipelines), Rule #33 (test on data chronologically after the training data), Rule #37 (measure training/holdout/next-day/live performance gaps) — [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Objectives: Rule #12 keep the directly-optimized objective simple; Rule #25 utilitarian (product) performance trumps raw predictive accuracy; Rule #39 launch decisions are proxies for multiple long-term goals — [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)

**Chip Huyen — Designing Machine Learning Systems (O'Reilly, 2022)**
- The book covers deployment modes (online, batch, stream prediction), why models fail in production, model monitoring, automated retraining, and online evaluation; Huyen taught Stanford CS 329S (ML Systems Design) and co-founded Claypot AI for real-time ML — [TWIML profile](https://twimlai.com/network/chip-huyen/); [QCon SF speaker page](https://qconsf.com/speakers/chiphuyen)
- Two levels of real-time ML: (1) online predictions in real time; (2) incorporating new data to update the model in real time (continual learning) — [QCon SF: Real-Time ML architecture and challenges](https://qconsf.com/presentation/oct2022/real-time-machine-learning-architecture-and-challenges)
- Named anti-patterns/corrections: treating batch prediction as a prerequisite for online prediction (legacy infrastructure assumption); training-serving skew from mismatched feature extraction code; fixed retraining schedules without drift monitoring — [huyenchip.com](https://huyenchip.com/2022/01/02/real-time-machine-learning-challenges-and-solutions.html)

### Inferences
- The three sources are complementary layers: Sculley names what goes wrong (anti-patterns), Zinkevich prescribes process ordering (heuristic → simple model → features → optimization), and Huyen/Google MLOps define the target architecture (automated pipelines, feature store, registry, continual learning) that structurally prevents the anti-patterns.
- The ML Design Patterns book's Workflow Pipeline, Transform, and Feature Store patterns are direct architectural remedies for Sculley's pipeline jungles, training-serving skew, and data-dependency debt respectively.

### Gaps
- Exact Chip Huyen book chapter text (e.g., her "deployment myths" chapter and the Netflix 4-hour batch-recommendation example) was only available via secondary summaries in this pass, not the book itself; the blog post and talk pages above are her first-party statements.
- The "correction cascades" definition is from the paper itself; note that some secondary summaries conflate it with the mercari "multiple stage prediction" pattern — they are distinct (deliberate staged serving vs. accidental training-time coupling).
